## User Input

```text
$ARGUMENTS
```

Аргумент — номера PR (можно через пробел, можно с `#`).

## Какой PR мержим, если номер не назван

**Пусто — значит PR текущей сессии.** Это общее правило для всех команд, принимающих номер PR
(`/merge`, `/code-review`, скилл `review`) — оно же записано в `CLAUDE.md`, раздел
«The current PR». Определяй цель в этом порядке, не перескакивая:

1. **По текущей ветке.** Это основной способ: сессия, которая вела issue, сидит в своём
   worktree на своей ветке.

   ```bash
   git rev-parse --abbrev-ref HEAD
   gh pr list --head <branch> --state open --json number,title,headRefName
   ```

   Нашёлся ровно один открытый PR — это он, мержим без переспрашивания: команду запустил
   человек, значит разрешение есть.

2. **Если ветка — `develop`** (сессия работает в основном каталоге, а не в worktree), своей
   ветки у неё нет. Тогда возьми PR, с которым эта сессия работала по ходу разговора: она его
   открывала, гоняла на нём ревью или синхронизировала. Назови его человеку вместе с
   обоснованием, откуда взяла, и мержи.

3. **Если и это не определилось** — не угадывай. Покажи открытые PR, у чьих issue стоит
   `status: ready to merge`, и **дождись, какой именно**:

   ```bash
   gh issue list --label "status: ready to merge" --state open --json number,title
   ```

4. **Если ветка нашлась, но открытого PR на неё нет** — скажи об этом прямо: работа не доведена
   до PR, мержить нечего. Предложи закончить цикл через `/github-issue`.

Нашлось несколько открытых PR на одну ветку — это ненормально, покажи их и спроси, какой.
Никогда не «мержим всё, что готово» по молчанию: пустой аргумент означает **одну** цель.

## Назначение

Это тот самый шаг, который в `/github-issue` намеренно не автоматизирован: merge в `develop`.
**Запуск этой команды человеком и есть разрешение на merge** — если цель определена однозначно
(номер назван явно либо однозначно вывелся из текущей ветки), дополнительно спрашивать не нужно.
Всё остальное команда обязана проверить сама.

Типичный сценарий: сессия довела issue до `status: ready to merge`, остановилась и спросила
человека; человек отвечает «мержим» — и команда запускается без аргумента, потому что речь
очевидно про её собственный PR.

## Правила, которые нельзя нарушать

- **Никогда не продавливай merge мимо падающих проверок.** `--admin`, `--force`, отключение
  требований — запрещено. Не проходит проверку — не мержим, а докладываем.
- **Не мержи PR, который не готов.** Готовность определена ниже; не сошлось хоть одно
  условие — этот PR пропускаем и объясняем, чего не хватает.
- **Отставшую ветку и конфликты не «пропускаем», а доводим.** Синхронизация с `develop` и
  разрешение конфликтов — штатная часть этой команды (шаг 2). Останавливаемся и спрашиваем
  только там, где непонятно, какое поведение правильное, — но в этом случае останавливаемся
  обязательно: молча выбранная сторона в спорном конфликте тихо теряет чужую работу.
- **После разрешения конфликта заново гоняем гейты и CI**, а если поменялась логика —
  и ревью. Код, появившийся при мерже, ревью ещё не видел.
- **Squash, а не merge-коммит.** Политика `CLAUDE.md` (Rule 1): одна фича = один squash-коммит
  на `develop`, и вся текущая история именно такая. Заголовок squash-коммита — заголовок PR,
  он обязан быть Conventional Commit с номером issue. `delete_branch_on_merge` в настройках
  репозитория **выключен**, поэтому удаление ветки указываем явно.
  Исключение бывает: PR, который сознательно должен лечь несколькими коммитами (крупная
  консолидация с осмысленной историей), мержится rebase-ом — но **только** если человек сказал
  это явно в этом разговоре или в теле PR стоит такое требование. Сам стиль не меняй.
- **По одному PR за раз, последовательно.** После каждого merge остальные PR становятся
  отставшими от `develop` — их нужно переоценить заново, а не мержить пачкой.
- **Пустой аргумент — это одна цель, а не «всё готовое».** Мержить пачкой можно только тогда,
  когда человек назвал несколько номеров явно.
- Репозиторий строго один — тот, что в `git config --get remote.origin.url`
  (`quantum-soft-dev/data-forge-middleware`).

## Шаги

### 1. Собрать статус

```bash
git fetch origin develop
gh pr view <pr> --json number,state,isDraft,baseRefName,headRefName,mergeable,mergeStateStatus,body,statusCheckRollup
gh pr checks <pr>
gh pr view <pr> --comments
```

`mergeStateStatus` — главный сигнал, читай его буквально:

| Значение | Что значит | Что делать |
|---|---|---|
| `CLEAN` | готов к merge | шаг 3 |
| `BEHIND` | ветка отстала от `develop`, конфликтов нет | шаг 2, синхронизация |
| `DIRTY` | конфликты с `develop` | шаг 2, разрешение |
| `BLOCKED` | не пройдены требования ветки (проверки, ревью, approve) | не мержим, объясни, чего требует настройка ветки |
| `UNSTABLE` | смержить можно, но проверки не все зелёные | разбери, что именно красное, прежде чем решать |
| `UNKNOWN` | GitHub ещё считает | подожди и перечитай, не считай это ошибкой |

`mergeable` вычисляется лениво: если пришло `UNKNOWN`, перечитай через пару секунд, а не делай
вывод по первому ответу.

Кроме `--comments` прочитай inline-треды и review states — GraphQL-срез и правила чистоты
описаны в `/github-issue`, шаг 8. `gh pr view --comments` их не возвращает, и PR с открытым
inline-замечанием выглядит через него чистым.

И прочитай `GetDiffComments` — комментарии человека на дифе в панели Changes. Их в `gh` нет
вообще, а незакрытый комментарий там значит ровно то же, что unresolved-тред: не мержим.

### 2. Синхронизация и разрешение конфликтов

Нужна при `BEHIND` и `DIRTY`. Это **часть merge-процесса**, а не повод отказаться: цель —
довести ветку до состояния, в котором merge безопасен.

Работай там, где эта ветка уже выложена, — не создавай вторую копию:

| Где ты | Где синхронизировать |
|---|---|
| Сессия сидит на **этой же ветке** (обычный случай: свой Conductor-workspace) | прямо здесь, `git merge origin/develop` |
| Ветка выложена в другом worktree (`git worktree list`) | там, `git -C <путь> merge origin/develop` |
| Ветки нет нигде | временный worktree: `git worktree add .worktrees/<n>-<slug> <branch>`, в конце убрать |

Никогда не выкладывай ветку второй раз, если она уже занята чужим worktree, — git этого и не
даст, а обход через detached HEAD превращает merge в потерю коммитов.

```bash
git merge origin/develop        # или git -C <путь к worktree> merge origin/develop
```

**При `BEHIND`** merge пройдёт сам. Всё равно прогони гейты: чужие изменения из `develop` могли
разойтись с твоими по смыслу, даже не конфликтуя текстуально.

**При `DIRTY`** — разрешай осмысленно:

```bash
git diff --name-only --diff-filter=U      # с -C <путь>, если работаешь в чужом worktree
```

- По каждому конфликтующему файлу разберись, **что именно** менялось с обеих сторон:
  `git log --oneline origin/develop ^HEAD -- <файл>` покажет, что пришло из `develop`.
- Не выбирай сторону вслепую. `--ours` / `--theirs` целым файлом — только если ты понял, что
  вторая сторона этот файл не меняла по существу.
- Особый случай — накопительные и процессные файлы: `CLAUDE.md` (особенно «Recent Changes»),
  `specs/**/tasks.md`, `docs/`. Там почти всегда нужно **объединить обе записи**, а не выбрать
  одну.
- По каждому конфликту скажи человеку, что выбрал и почему. Это отчёт, а не служебная деталь:
  именно здесь чаще всего теряются чужие изменения.

**Отдельно и всегда — номера Flyway-миграций.** Это конфликт без конфликта: обе ветки добавили
`V49__…`, git взял оба файла молча, а приложение упадёт на старте (и в Testcontainers-тестах).
После merge:

```bash
ls src/main/resources/db/migration/ | sort -V | tail -5
```

Два файла с одним номером — переименуй **свой** на следующий свободный и поправь ссылки на него
в тестах и доках. То же самое, но тише, — номера полей в `src/main/proto/delta-ingestion.proto`
и номера каталогов `specs/NNN-*`: их коллизию тоже никто не подсветит.

Дальше обязательно:

1. Гейты зелёные там же, где мержил: `./gradlew test -PexcludeIntegration`,
   `./gradlew integrationTest` (нужен запущенный Docker), а если трогали фронт —
   `npx tsc --noEmit`, `npm --prefix frontend run lint`, `npm --prefix frontend test`.
   В свежем worktree сначала `npm --prefix frontend ci` — `node_modules` гитом не носятся.
2. Закоммить merge и запушь.
3. Дождись, пока CI на PR снова позеленеет: `gh pr checks <pr> --watch --interval 20`.
   Актуальные гейты — `backend-test` и `frontend-test`.
4. **Если разрешение конфликта поменяло логику, а не просто склеило соседние строки** —
   прогони ревью заново (`/code-review <pr>` или скилл `review`, если плагин уже отработал по
   этому PR). Изменённый при мерже код ревью ещё не видел. Если синхронизация принесла только
   документацию и CI-конфиг, продуктовый код не менялся — повторное ревью не нужно, но скажи
   об этом явно.

Если конфликт содержательный и ты не уверен, какое поведение правильное — **остановись и
спроси**. Молча выбранная сторона в спорном конфликте — это тихая потеря чужой работы.

### 3. Повторная проверка готовности

После шага 2 факты устарели — собери их заново и сверься со всеми условиями:

| Условие | Как проверить |
|---|---|
| PR открыт и не draft | `state == OPEN`, `isDraft == false` |
| Целевая ветка — `develop` | `baseRefName == develop` |
| Состояние merge | `mergeStateStatus == CLEAN` |
| Все проверки зелёные | `statusCheckRollup` |
| Гейты актуальны | среди проверок есть `backend-test` и `frontend-test` |
| Ревью чистое | нет unresolved `reviewThreads`, видимых `PENDING` reviews и `CHANGES_REQUESTED` |
| Панель Changes чистая | в `GetDiffComments` нет неразобранных комментариев |
| Заголовок PR годится в коммит | Conventional Commit + `(#<n>)` — он станет squash-коммитом |
| Issue закроется сам | в теле PR есть `Closes #<n>` |
| Тикет помечен готовым | у issue метка `status: ready to merge` |

- **Нет `Closes #<n>`** — не выдумывай связь по имени ветки как единственный источник. Скажи
  человеку, что issue придётся закрывать вручную, и уточни номер, если он неочевиден.
- **Заголовок PR не годится в историю** (нет типа, нет области, нет номера issue) — поправь
  его до merge: `gh pr edit <pr> --title "..."`. После squash это уже не исправить.

### 4. Merge

```bash
gh pr merge <pr> --squash --delete-branch
```

Проверь результат: `gh pr view <pr> --json state,mergedAt,mergeCommit`. Отработавшая без
ошибки команда — не доказательство того, что PR смержен.

### 5. Закрыть тикет и довести доску

Номер issue берётся из `Closes #<n>` в теле PR.

1. **Issue закрыт?** `gh issue view <n> --json state,closedAt`. Если `Closes` не сработал —
   закрой явно: `gh issue close <n> --comment "Смержено в develop: PR #<pr>"`.
2. **Карточка в `Done`?** Встроенный workflow проекта переносит её при закрытии issue, но
   проверь и подвинь руками, если не переехала. Идентификаторы доски — в `CLAUDE.md`, раздел
   «Board identifiers»; сюда их не копируй:

   ```bash
   gh project item-list 16 --owner quantum-soft-dev --format json --limit 100
   gh project item-edit --project-id <project-id> --id <PVTI_...> \
       --field-id <status-field-id> --single-select-option-id <option-id колонки Done>
   ```

3. **Снять статусные метки.** Закрытый тикет не должен висеть с `status: ready to merge`:

   ```bash
   gh issue edit <n> --remove-label "status: ready to merge" --remove-label "status: in review"
   ```

   Метки `bug`/`enhancement` и `priority: *` не трогаем — это классификация, а не статус.

4. **Если PR поглотил ещё один тикет** (в теле PR или в issue написано `folds #NNN`, «сворачивает
   #NNN»), закрой и его — с меткой `duplicate`:

   ```bash
   gh issue edit  <NNN> --add-label duplicate
   gh issue close <NNN> --comment "Поглощён #<основной>, смержено в develop: PR #<pr>."
   ```

   Метка обязательна и здесь тоже (`CLAUDE.md` → «A ticket closed as absorbed carries
   `duplicate`»), хотя работа как раз **уехала** в `develop` вместе с поглотителем: `duplicate`
   помечает исход «закрыт чужой работой, а не своим PR», а не «не исправлено». Ровно это и делает
   её пригодной — закрывающий не обязан угадывать будущее поглотителя. Что именно случилось,
   говорит комментарий; здесь он говорит «смержено». Карточку из `Done` не двигай — отдельной
   колонки под этот исход нет намеренно, её перезаписал бы тот же встроенный workflow.

### 6. Убрать за собой

Убирается только то, что ты создавал:

```bash
git worktree remove .worktrees/<n>-<slug>   # если worktree заводила эта команда или /github-issue
git worktree prune
git fetch origin develop
```

**Conductor-workspace не удаляй и не пытайся архивировать** — это делает человек в приложении
(или настройка «Auto-archive on PR close»); ты про него просто говоришь, что он свободен. И не
удаляй worktree, в котором прямо сейчас сидит чужая сессия: сверься с `git worktree list` и
спроси, если не уверен.

Локальный `develop` в основном рабочем каталоге **сам не переключай и не подтягивай молча**:
там могут быть незакоммиченные изменения. Скажи, на сколько коммитов он отстал, и предложи
подтянуть.

Merge в `develop` **ничего не деплоит**. Dev (GKE) выкатывается только тегом:
`TAG=deploy-dev/$(date +%Y%m%d-%H%M); git tag $TAG && git push origin $TAG` — и делает это
человек, а не ты. Если изменение нужно на стенде, скажи об этом в отчёте и предложи тег.

### 7. Отчёт и следующий шаг

По каждому PR скажи: смержен или пропущен и почему, каким коммитом, закрылся ли issue,
где оказалась карточка, убран ли worktree. Если была синхронизация — что именно пришло из
`develop`, а при конфликтах перечисли файлы и выбранные решения. Отдельно перечисли то, что
требует внимания человека.

Если PR было несколько — после каждого merge **переоцени оставшиеся** с шага 1: они гарантированно
стали `BEHIND`, а некоторые могут стать `DIRTY`, и у части разъедутся номера миграций.
Каждому проводи шаг 2 заново. Не мержи их подряд, не перепроверив.

В конце предложи следующий шаг: взять следующий issue из спринта (`/github-issue <n>`),
синхронизировать отставшие PR, выкатить тег на dev или остановиться.

## Побочные находки

Если при синхронизации или разрешении конфликтов всплыло что-то за рамками этого PR, порядок
такой же, как в `/github-issue`:

1. **Сначала поиск** — `gh issue list --state all --search "<ключевые слова>"` и `grep` по
   `CLAUDE.md` и `docs/`. Возможно, тикет уже есть (тогда дополни его комментарием) или уже
   закрыт (тогда это либо регрессия — новый issue со ссылкой на старый, — либо твоё наблюдение
   устарело и тикет не нужен).
2. **Потом GitHub issue**, если ничего не нашлось: с описанием, метками, milestone, `Backlog`
   на доске. Плюс **три строки про пересечения** (`CLAUDE.md` → «Every follow-up says what it
   will touch»): какие файлы тронет, нужна ли Flyway-миграция или каталог `specs/NNN-*`, и какие
   открытые тикеты живут в тех же файлах («none found» — валидный ответ).
3. Работу по нему здесь не начинаем — назови номер человеку и предложи взять его следующим.

## Если что-то пошло не так

- Merge прошёл, а issue не закрылся и карточка не переехала — доведи вручную и скажи об этом.
  Наполовину закрытый тикет хуже незакрытого: он выглядит сделанным, а доска врёт.
- `gh pr merge` отказал из-за защиты ветки — не обходи. Покажи текст отказа.
- После merge упал CI на `develop` — сразу скажи, не откладывая до конца отчёта.
