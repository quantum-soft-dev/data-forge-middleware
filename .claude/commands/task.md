---
description: Выполнить issue data-forge-middleware от взятия до squash-merge в его базовую ветку (develop, если тикет не объявил другую)
argument-hint: <issue#>
---

Выполни issue #$ARGUMENTS репозитория `quantum-soft-dev/data-forge-middleware` по конвейеру ниже.
Нормативный источник процесса — `CLAUDE.md` (разделы «Development Policy» и «Working from a GitHub
issue»); при расхождении по существу действует он — **кроме шагов 3 и 6, где расхождения объявлены
явно**: безусловный worktree и merge собственного PR.
`.specify/memory/constitution.md` — незаполненный шаблон спек-кита, на него не ссылайся.

1. **Взять.** `gh issue view $ARGUMENTS --json title,body,labels,milestone,comments` — **обязательно с
   комментариями**: здесь уточнение объёма регулярно живёт в комментарии, а не в теле, и тикет,
   прочитанный без них, решается не тот. Блокировку разбирай **по трём случаям, а не по одной
   метке**: открыта хотя бы одна `Blocked by #N` → стоп, сообщи; метка `status: blocked` есть, а строк
   `Blocked by` в теле нет → тоже стоп и вопрос человеку (блокировка ручная, по внешней причине, и
   `board.sh unblock` её не тронет — у неё пустой список зависимостей); все `Blocked by` закрыты, а
   метка висит → метка протухла (блокер закрыли мимо `unblock`): `scripts/board.sh unblock <каждый
   закрытый блокер>` и продолжай. Такие метки по всей доске сразу находит `scripts/board.sh sweep`.
   Прогони `scripts/issue-find.sh "<ключевые слова>" <пути>`:
   задача уже решена смерженным PR или дублирует закрытую → сообщи и не начинай. Затем определи
   базу (абзац ниже), и только потом — в этом порядке — `gh issue edit $ARGUMENTS --add-assignee @me`
   (сначала назначение: автоматизация доски реагирует на события, и переход, сделанный до них, может
   быть перебит), майлстоун текущего спринта, `scripts/board.sh status $ARGUMENTS "In Progress"`
   (из `Backlog` — сначала `Ready`: колонки не перепрыгивают). **После каждого перехода сверяй
   колонку, которую напечатал `board.sh`, с запрошенной** — он перечитывает её с доски; разошлись —
   повтори переход один раз, снова разошлись — скажи человеку: доску перебивает её автоматизация.
   Метки `status: *` ставит **только** `board.sh`: прямой `gh api …/labels` переставит метку, но не
   колонку, и доска начнёт врать молча. Если `board.sh` (или `gh`) отвечает `INSUFFICIENT_SCOPES` —
   остановись и скажи выполнить `gh auth refresh -s project`; любой другой отказ `board.sh` — тоже
   стоп, а не обход руками.

   **База тикета — до назначения и доски.** `scripts/issue-base.sh $ARGUMENTS` печатает `<base>`:
   `develop`, либо ветку миграции из строки `` Base branch: `migration/<name>` `` в начале тела
   (`CLAUDE.md` → Rule 1). Правило чтения (только до первого заголовка и вне кода) живёт в скрипте —
   не пересказывай и не читай строку глазами. Скрипт отказал (код ≠ 0) → стоп и сообщи его текст,
   карточку не трогай: кривая строка не значит `develop`, а тикет миграции с PR в `develop` — ровно
   то, что эта проверка ловит. `<base>` ≠ `develop` → ветка должна существовать
   (`git ls-remote --exit-code --heads origin <base>`), иначе стоп. Ниже `<base>` стоит везде, где
   речь о ветвлении, синхронизации, базе PR и цели merge.

2. **Понять.** Прочитай `CLAUDE.md` — вместе с записями «Recent Changes» по затронутой подсистеме:
   там записаны не только принятые решения, но и отклонённые вместе с причинами, и это дешевле, чем
   предложить отвергнутое второй раз. Затем ТОЛЬКО разделы документов, на которые ссылается issue
   (`grep -n '^#' docs/<файл>.md` → `sed -n '<от>,<до>p'`), и существующие тесты затронутой области.
   Опубликуй план комментарием в issue (5–15 строк): какие файлы, нужна ли Flyway-миграция и какой
   номер свободен (`ls src/main/resources/db/migration/`), нужен ли `specs/NNN-*`, какие тесты станут
   красными первыми. Открытый вопрос или противоречие с ранее принятым решением → вопрос с вариантами
   и рекомендацией в чат И в issue, `scripts/board.sh status $ARGUMENTS Blocked`, стоп (если worktree
   уже создан — оставить, `ExitWorktree keep`).

3. **Сделать.** Сначала worktree: если `git worktree list` уже содержит `.claude/worktrees/$ARGUMENTS-*`
   (или `.worktrees/$ARGUMENTS-*` от `/github-issue`) — `EnterWorktree` с `path` к нему, второй не
   создавать; иначе `EnterWorktree` с именем `$ARGUMENTS-<slug>` (создаётся в `.claude/worktrees/` от
   `origin/develop` при любой базе), затем внутри `git fetch origin <base>` и
   `git switch -c <type>/$ARGUMENTS-<slug> origin/<base>` — ветка от **базы**, а не от того, на чём
   стоит worktree (`bug` → `fix/`,
   `enhancement` → `feature/`, иначе `chore/`; полноценная спек-фича — `feature/NNN-name`). В свежем
   worktree подними то, что гитом не носится: `git config core.hooksPath .githooks`,
   `npm --prefix frontend ci`, `cp` гитигнорнутых `frontend/.env.local` и `local-dev/auth0.env`. Все
   дальнейшие команды — из worktree; в основной рабочей копии код не писать.

   > **Первое исключение, объявленное явно.** `CLAUDE.md` называет вложенный worktree внутри
   > Conductor-workspace ошибкой: диф-вьюер, панель Checks и `GetWorkspaceDiff` показывают ветку
   > **workspace'а**, поэтому работа во вложенном worktree в приложении не видна. `/task` всё равно
   > создаёт worktree безусловно — это выбор владельца процесса, а не недосмотр: команда рассчитана
   > на автономный прогон, который сам же и мержит, так что промежуточная видимость в приложении не
   > является для неё рабочим инструментом. Практическое следствие: запуская `/task` **внутри**
   > Conductor-workspace, следи за ходом по PR на GitHub, а не по панели Changes. Нужна видимость в
   > приложении — бери `/github-issue`, он работает прямо в ветке workspace'а.

   TDD, строго по одной задаче (WIP = 1): красный тест → минимальная реализация → зелёный → рефактор,
   коммит по завершении задачи. **Тест, который не может упасть, — не тест**: если свойство уже
   держится, докажи мутацией — сломай продакшн-строку, покажи, какие тесты покраснели, и назови
   мутацию в PR. Меняешь подход по ходу — удали устаревшие тесты и напиши новые (Rule 2.4), не
   оставляй тесты, не описывающие принятое решение.

   Гейт перед каждым коммитом: `./gradlew test -PexcludeIntegration` (нужен Docker — около 30
   контрактных тестов на Testcontainers; без него гейт умирает внутри `Unsafe.java`, это не «тесты
   упали»). Трогал фронт — ещё `npx tsc --noEmit` из `frontend/`, `npm --prefix frontend run lint`
   (`--max-warnings 0`) и `npm --prefix frontend test`. `--no-verify` запрещён политикой.
   Коммиты — Conventional Commits **по-английски**, как вся история репозитория, со ссылкой на issue:
   `fix(delta): … (#$ARGUMENTS)`.

   Одна проблема не решается с 3 попыток → стоп и вопрос. Работа по факту вдвое больше объёма issue →
   стоп, предложить разбиение.

4. **Проверить.** `git pull --rebase origin <base>`; `./gradlew integrationTest` (Testcontainers) +
   фронтовые гейты, если фронт трогался. Каждый критерий приёмки → каким тестом доказан. Трогал UI —
   открой изменённый экран в браузере и приложи скриншот в PR: тест компонента не показывает, как
   экран выглядит. Документация
   едет вместе с кодом (Rule 1): запись в «Recent Changes» `CLAUDE.md` и/или `docs/` (`cr-*.md` для
   изменения дизайна, клиентский гайд для видимого поведения) — по каждой поверхности скажи «нужно»
   или «не нужно», молча не пропускай; корневой `CHANGELOG.md` заморожен, не воскрешай.

   Push, PR в базу — `gh pr create --base <base>` — с `Closes #$ARGUMENTS`, разделом
   «Удалённые/изменённые тесты» (если были) и названной мутацией из шага 3. При `<base>` ≠ `develop`
   `Closes` issue **не закроет** (GitHub закрывает по ключевому слову только при merge в ветку по
   умолчанию), но строку всё равно пиши: по ней `/merge` и диспетчер находят тикет, а закрытие
   делает шаг 6. Дождись CI: `gh pr checks --watch --interval 60` (не чаще — опрос тратит общий GraphQL-бюджет). На фиче-ветке CI — это
   `backend-test` и `frontend-test` (и на PR в `migration/**` тоже); `code-quality` и `dependency-analysis` гейтятся на
   `run_full_pipeline` (только `develop`/`release`/`main`), их отсутствие — не провал. Красный CI →
   чини, лимит 3 попытки; смотри, какой именно тест упал, а не списывай проверку.

5. **Ревью.** `scripts/board.sh status $ARGUMENTS "In Review"`. Запусти ПАРАЛЛЕЛЬНО трёх субагентов
   `review-correctness`, `review-contracts`, `review-architecture`, передав каждому номер issue,
   номер PR и ветку. Действуй только по SERIOUS; MINOR игнорируй (ценное → шаг 6, протокол находок).
   SERIOUS можно отклонить только доказательством — тест или цитата документа — и это записывается в
   PR. После правок: гейт коммита + `integrationTest`, push, повторно — только тот ревьюер, чьи
   SERIOUS исправлялись, по diff правок. Максимум 2 круга; не сошлось → вопрос человеку, стоп.

   Чисто — значит чисто на **всех** поверхностях, а не только в выводе субагентов:
   `gh pr view --comments` не показывает inline-треды, поэтому проверь `reviewThreads` — любой с
   `isResolved == false` блокирует, даже `isOutdated`; `PENDING`-ревью блокирует; текущий
   `reviewDecision == CHANGES_REQUESTED` блокирует. Закрытие inline-находки — ответ → публикация →
   `resolveReviewThread`, с перечитыванием состояния после каждой мутации (готовый GraphQL — в
   `/github-issue`, шаг 8).

6. **Смержить.** Три `VERDICT: READY`, зелёный CI и чистые поверхности ревью, и `baseRefName` PR
   совпадает с `<base>` из шага 1 → `scripts/pr-merge.sh <pr>`, затем `ExitWorktree` с `remove`
   (вернуться в основную копию). **Не** `gh pr merge --delete-branch`: из worktree gh мержит, а потом
   падает на локальной уборке (`fatal: '<base>' is already used by worktree`), и ветка остаётся
   (#332). Скрипт мержит squash-ем без локальной уборки, берёт вердикт из перечитанного PR, а не из
   кода выхода gh, и удаляет ветку через REST. Код `0` — смержен, ветка удалена; `1` — не смержен,
   текст отказа напечатан; `2` — отказ до любых действий; `3` — **смержен**, но ветка осталась: merge
   не повторять, удалить ветку командой из сообщения. Дальше порядок важен — `unblock` переводит в `Ready` только тикеты, у которых
   **все** блокеры уже закрыты:

   - `<base>` = `develop`: issue закрыл `Closes #$ARGUMENTS` — проверь `gh issue view $ARGUMENTS
     --json state`.
   - `<base>` ≠ `develop`: `Closes` не сработал и не сработает — закрой явно:
     `` gh issue close $ARGUMENTS --comment 'Merged into `<base>` by #<pr>.' `` — в **одинарных**
     кавычках: в двойных bash исполнит обратные кавычки как команду.

   Затем `scripts/board.sh status $ARGUMENTS Done` (он же снимает все `status: *`),
   `scripts/board.sh unblock $ARGUMENTS`, перечитать тикет — закрыт, в `Done`, без `status: *` — и
   отметить пункт в родительской issue, если есть.

   > **Второе исключение, объявленное явно.** Общее правило `CLAUDE.md` — «merge в `develop` делает только
   > человек»; для тикета миграции то же относится к её ветке. Для `/task` разрешением служит сам
   > вызов команды: запустив её, человек санкционировал merge этой задачи в её базу. Все проверки готовности при этом выполняются полностью — исключение снимает
   > вопрос, а не проверки. Соседние команды своё поведение не меняют, и они не одинаковы:
   > `/github-issue` разрешения **не** несёт — доходит до готовности и передаёт решение человеку;
   > `/github-issue-runner` несёт своё, на весь прогон; `/merge <pr>` и есть явная выдача разрешения
   > на один PR.

   Всё «не вошло» и побочные находки: `scripts/issue-find.sh "<слова>" <пути>` → та же проблема
   открыта → комментарий с твоими доказательствами; закрыта, но воспроизводится на текущем
   `origin/develop` → переоткрыть; похожая или в тех же файлах в `Backlog`/`Ready` → укрупнить её
   (объём + критерии, комментарий «добавлено из #$ARGUMENTS»); `In Progress`/`In Review` → только
   комментарий; ничего не нашлось → новая issue, сформулированная как **тема** (причина или
   подсистема), а не как один симптом — метки типа и `priority: *`, колонка `Backlog`, без
   майлстоуна; первая строка тела — `Предлагаемый майлстоун: <n> — <почему>`. Тело — разделами
   шаблона `.github/ISSUE_TEMPLATE/task.yml` (для бага — `bug.yml`), и обязательно с **«Что тронет»**
   (файлы, Flyway-миграция, `specs/NNN-*`) и **«Открытые тикеты в тех же файлах»**: при
   `gh issue create --body` форма не применяется, разделы пишутся руками. Работа по находке никогда
   не начинается в текущем цикле.

7. **Отчитаться и остановиться.** **Остановка до merge по любой причине** — вопрос человеку, чужой
   блокер, лимит в 3 попытки, объём вдвое больше тикета, ревью не сошлось за два круга, человек
   переключил на другое — сначала возвращает статус: `scripts/board.sh status $ARGUMENTS Blocked`, если
   ждём решения или чужой задачи, иначе `Ready`, со сверкой колонки; и только потом отчёт. `In Progress`
   на задаче, которую никто не ведёт, врёт доске: по ней нельзя ни собрать следующую волну, ни понять,
   что брошено. Короткий отчёт в чат: PR, что сделано, вердикты трёх ревьюеров, что
   не вошло (номера issues), разблокированные issues и **в какой колонке тикет остался на доске**.
   Следующую задачу НЕ начинать.

**Бюджет GitHub GraphQL** (`CLAUDE.md` → «GraphQL budget»): 5000 очков в час на аккаунт, общих на все
сессии и субагентов. НИКОГДА не запускай `gh project …` — всё по доске делает `scripts/board.sh` (смена
статуса — 3 очка вместо ~500). Метки, комментарии, тело и состояние issue читай и меняй через REST
`gh api repos/…` (0 очков). CI — `gh pr checks --watch --interval 60`, не чаще. Перед серией вызовов —
остаток через `scripts/wave.sh budget` (1 очко): `gh api rate_limit` для GraphQL показывает неверный
`used`.

Экономия токенов: не читай файлы целиком без нужды, не вставляй diff и логи в чат, фильтруй вывод
тестов (`-q`, смотри только падения), для широкого поиска по коду используй субагента `Explore`, не
перечитывай то, что уже читал в этой сессии. Комментарии в issue — три типа: **План**, **Вопрос**,
**Итог**; без «работаю…».
