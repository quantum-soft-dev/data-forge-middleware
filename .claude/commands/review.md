description: Прогнать три линзы ревью (correctness / contracts / architecture) по открытому PR — отчёт без правок и merge
argument-hint: [pr#] [issue#] [--comment]
---

Прогони по PR три линзы ревью из `/task` — и больше ничего: без правок, без merge, без движения
карточки на доске.

## Аргументы

`$ARGUMENTS` — до трёх токенов в любом порядке: номер PR, номер issue (`#` допустим) и флаг
`--comment`. Первое число — PR, второе — issue.

- **PR не назван** → PR текущей сессии по правилу `CLAUDE.md`, раздел «The current PR»: ветка
  (`git rev-parse --abbrev-ref HEAD` → `gh pr list --head <branch> --state open --json number,title`,
  ровно один → он); на `develop` — PR, над которым шла эта сессия, с указанием, откуда он взят;
  неоднозначно → перечисли кандидатов и спроси; ветка без открытого PR → скажи прямо и остановись.
- **Issue не назван** → `Closes #N` из тела PR (`gh pr view <pr> --json body,headRefName,state`).
  Не нашёлся — продолжай, но сообщи, что критерии приёмки проверять не по чему, и вынеси это в отчёт.
- PR закрыт или смержен → скажи и остановись.

## Ревью

Запусти **параллельно** (одним сообщением) субагентов `review-correctness`, `review-contracts` и
`review-architecture`, передав каждому номер issue, номер PR и ветку (`headRefName`). Diff и файлы
каждый получает сам — не пересказывай им ни изменения, ни свою гипотезу.

Ответ линзы без строки `VERDICT:` в ожидаемом формате (сбой, обрыв, свободный текст) — это **«нет
вердикта»**, а не `READY`: молчание не означает «замечаний нет». Такую линзу перезапусти один раз;
повторилось — так и укажи в отчёте.

## Отчёт

Одна таблица, затем SERIOUS списком:

| Линза | VERDICT | SERIOUS | MINOR |
|---|---|---|---|
| review-correctness | READY / CHANGES / нет вердикта | число | число |
| review-contracts | … | … | … |
| review-architecture | … | … | … |

Под таблицей — все SERIOUS дословно, сгруппированные по линзам (`[file:line] claim — evidence —
fix`). MINOR показывай только числом. Итог одной строкой: **READY только если все три линзы дали
`READY`**, иначе CHANGES.

Команда оценивает **только три линзы**. Остальные поверхности готовности — CI, inline-треды
(`reviewThreads`), `PENDING`-ревью, `reviewDecision`, комментарии человека на дифе в Conductor —
здесь не проверяются, и READY этой команды не означает, что PR можно мержить. Готовность решают
`/task` (шаги 5–6), `/merge` и `/github-issue` (шаг 8).

## `--comment`

Без флага ничего не публикуется — отчёт только в чат.

С флагом опубликуй ту же таблицу и SERIOUS **одним** комментарием к PR (`gh pr comment <pr>
--body-file <файл>`), заголовок — `Review lenses — round <N>`, где N — число таких комментариев в
PR плюс один. Так ревью видно в PR, как требует `CLAUDE.md` («The review loop is visible in the
PR»): на это опирается `/github-issue` на втором и последующих кругах, когда `/code-review` по PR уже
отработал. Ответ на каждую находку после правок — работа исполнителя, не этой команды.

Экономия токенов: сам diff не читай и в чат не вставляй — его читают линзы.
