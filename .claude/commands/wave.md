Ты — **координатор волны** (`CLAUDE.md` → «Running several issues at once» и «GraphQL budget»; при
расхождении по существу главнее `CLAUDE.md`). Аргумент: `$ARGUMENTS` — число `N` (размер волны, 1–3, по
умолчанию 3; **три — жёсткий потолок**, `N > 3` не берётся ни по просьбе, ни после предупреждения),
`plan` (только расчёт, ничего не менять), `resume` (продолжить прерванную волну, шаг R) или `health`
(проверка здоровья сессий, шаг H; её раз в час вызывает расписание волны). Волна держит до `N` задач в
работе всё время: освободился слот — добор (шаг Д).

**Вызов `/wave` — разрешение человека на merge задач этой волны в их базы** — то же исключение из «merge
делает только человек», что у `/task` и `/github-issue-runner`, выданное на эту волну, а не навсегда. Оно
снимает вопрос, а не проверки: каждое условие готовности ниже проверяется полностью.

`/wave` — автономный режим диспетчера: исполнители — фоновые субагенты `task-runner`, каждый в своём
worktree `.claude/worktrees/<n>-<slug>`. Нужен режим, где задачи идут в видимых workspace'ах человека
(Conductor), — это `/github-issue-runner` в режиме A; обе команды не запускаются одновременно.

Ты работаешь в **основной рабочей копии** на `develop` и кода задач не пишешь — это делают исполнители.
Ты единственный, кто двигает карточки задач волны: **после каждого `scripts/board.sh status` сверяй
напечатанную колонку с запрошенной**; разошлись — повтори один раз; снова разошлись — это отказ (ниже).
**`board.sh` отказал** (ошибка, `INSUFFICIENT_SCOPES` — тогда `gh auth refresh -s project`, кончился
бюджет) — новые переходы и merge не начинать, метки руками не ставить, отчёт человеку. Журнал волны
(`scripts/wave.sh mark`) обновляется **сразу после каждого подтверждённого перехода** — он источник истины
для сверки и для `resume`.

## 0. Подготовка

`git status --porcelain` пуст и ветка `develop` (иначе — стоп и сообщить); `git pull --ff-only origin
develop`; `scripts/wave.sh budget` (1 очко; `gh api rate_limit` для GraphQL врёт — показывает `used: 0`,
когда очки уже списаны).

## 1. Расчёт

`scripts/wave.sh plan <N>`. Код выхода 3 — есть незакрытый журнал: при `resume` — шаг R, иначе
`scripts/wave.sh verify` и вопрос человеку (AskUserQuestion): «продолжить (`/wave resume`)» или «закрыть как
прерванную (`scripts/wave.sh end --interrupted`)» — стоп до ответа. Код 4 — мало GraphQL-очков: отчёт и
стоп. Ни одной строки `PICK` — отчёт с причинами отсева и стоп. При `plan` — показать выбор и отсев и
остановиться.

**Порядок логический, а не только по меткам.** Скрипт сортирует по майлстоуну, метке `priority:*`, числу
разблокируемых задач, Size и номеру, и не ставит рядом задачи с общим ключом из «Что тронет» (файл,
`flyway`, `specs`, `proto`, `stand`). Этого мало для двух вещей, и их ты проверяешь сам до `begin`:

- **зависимость без `Blocked by`** — контракт, рефакторинг, миграция или инфраструктура раньше своих
  потребителей: читай тела PICK-задач и тех, что в «Занято»; обнаружил — оставь потребителя на добор;
- **`files?`** — тикет старше правила о «Что тронет»: молчание не значит «пересечений нет». Проверь
  grep-ом по названным в теле классам и путям против остальных PICK и задач в работе; пересечение — убрать
  его из волны.

Покажи человеку план коротко (PICK-строки + сводка SKIP по причинам, включая расхождения доски) и сразу
продолжай.

## 2. Взятие (по одной задаче, последовательно)

`scripts/wave.sh begin --size <N> <номера PICK>` (`N` — размер волны из аргумента, а не число PICK: по нему
считаются слоты добора). Сразу за ним — **расписание здоровья**: `CronCreate` с `cron: "<M> * * * *"`
(минута `M` — любая, кроме 0 и 30), `prompt: "/wave health"`, `recurring: true`; id держи до конца волны
(шаг 7 его снимает). Затем для каждой задачи:

1. Карточка в `Backlog` → сначала `scripts/board.sh status <n> Ready` + сверка (колонки не перепрыгивают).
   Затем `gh issue edit <n> --add-assignee @me`, **потом** `scripts/board.sh status <n> "In Progress"`.
   Сверка колонки; не сошлось после повтора → `scripts/board.sh status <n> Ready`,
   `scripts/wave.sh mark <n> Ready - "исключена: доска перебивает переход"`, задача выпадает из волны, слот
   освобождается — после взятия остальных добор (шаг Д).
2. Сошлось → `scripts/wave.sh mark <n> "In Progress"`.
3. Worktree: `git fetch -q origin`, база — из колонки `base=` строки PICK (ветка миграции должна
   существовать: `git ls-remote --exit-code --heads origin <база>`), slug — 2–4 английских слова из
   заголовка через дефис, `git worktree add --detach .claude/worktrees/<n>-<slug> origin/<база>`. Ветку
   создаёт исполнитель (`<type>/<n>-<slug>`: `bug` → `fix/`, `enhancement` → `feature/`, иначе `chore/`).
   `EnterWorktree` не вызывать — он переключит саму сессию координатора.

## 3. Запуск

**Одним сообщением** — по вызову Agent на задачу: `subagent_type: task-runner`, `run_in_background: true`,
`description: "Wave #<n>"`, prompt: `MODE: START`, `issue: #<n>`, `base: <база>`, `worktree: <абсолютный
путь>`. Id агента — в журнал: `scripts/wave.sh mark <n> "In Progress" - "agent=<id>"`.

Дальше ты **только реагируешь на уведомления** — не опрашивай, не спи, не угадывай результат, пока
уведомление не пришло. Человек пишет в чат — ответь, волна идёт дальше. Единственное плановое действие без
уведомления — почасовой `/wave health` (шаг H). Фоновых циклов ожидания сам не заводишь: CI проверяешь
разовым `gh pr checks`, результат исполнителя приходит уведомлением.

## 4. Реакция на результат исполнителя (блок `WAVE-RESULT`)

- **`READY_FOR_REVIEW`**: сам проверь `gh pr checks <pr>` (один раз, без `--watch`) — `backend-test` и
  `frontend-test` зелёные (`code-quality`/`dependency-analysis` на фиче-ветке не запускаются — это не
  провал), в теле PR есть `Closes #<n>`, `baseRefName` = база из журнала; нет — вернуть исполнителю
  `MODE: FIX` с этим пунктом. Затем `scripts/board.sh status <n> "In Review"` + сверка,
  `scripts/wave.sh mark <n> "In Review" <pr>`, и **параллельно в фоне** три ревьюера — `review-correctness`,
  `review-contracts`, `review-architecture` — каждому номер issue, номер PR, ветку.
- **`STOPPED`**: `scripts/board.sh status <n> <want_status>` (`Blocked` — ждём решения или чужую задачу;
  `Ready` — ничего не начато и ждать нечего) + сверка, `scripts/wave.sh mark <n> <want_status> <pr|->
  "<reason>"` (причина обязательна: по ней журнал отличает вернувшуюся задачу от ещё не взятой). Worktree
  остаётся. Вопрос — в отчёт (в issue его уже написал исполнитель; проверь, что комментарий есть). Слот
  освободился — добор (шаг Д).
- **Исполнитель упал или вернулся без `WAVE-RESULT`**: выясни факты — `git -C <worktree> log --oneline
  origin/<база>..HEAD`, открытый PR ветки (`gh api 'repos/quantum-soft-dev/data-forge-middleware/pulls?state=open&head=quantum-soft-dev:<ветка>'`)
  и его CI. PR есть и CI зелёный → как `READY_FOR_REVIEW`. Иначе → `Blocked` + сверка, комментарий в issue
  «исполнитель волны остановился без результата на шаге …; worktree `<путь>` сохранён; продолжить —
  `/task <n>`», журнал. **Карточка задачи волны не остаётся в `In Progress` без живого исполнителя —
  никогда.**
- **`new_issues`** в любом результате: каждую — `scripts/wave.sh mark <new> <колонка> - "новая из #<n>"`,
  чтобы её проверила сверка.
- **`FIXED` / `REBASED`** — шаги 5–6.

## 5. Ревью

Когда по PR вернулись все запущенные ревьюеры — опубликуй сводку одним комментарием в PR (таблица: линза →
VERDICT → SERIOUS; MINOR — числом), как делает `/review <pr> --comment`: петля ревью видна в PR.

- Три `VERDICT: READY` → проверь **остальные поверхности ревью** (`CLAUDE.md` → «The review loop is visible
  in the PR»): ни одного `reviewThreads` с `isResolved == false` (даже `isOutdated`), нет `PENDING`-ревью,
  `reviewDecision` ≠ `CHANGES_REQUESTED` (готовый GraphQL — `/github-issue` шаг 8, 1 очко). Чисто → PR в
  **очередь merge** (шаг 6). Не чисто → как SERIOUS.
- Есть SERIOUS → `SendMessage` исполнителю: `MODE: FIX`, круг k, SERIOUS дословно с именем ревьюера.
  Исполнитель недоступен — новый `task-runner` с `MODE: FIX` и тем же worktree. После `FIXED` — ответ в PR
  на каждую находку (исправлено sha / отклонено с доказательством) и повторно **только** ревьюеры, чьи
  SERIOUS исправлялись, по diff правок. Карточка остаётся `In Review`.
- Не сошлось за 2 круга → `Blocked` + сверка, комментарий-вопрос в issue и PR, журнал, в отчёт; слот
  освободился — добор (шаг Д). MINOR — не действовать (ценное → протокол находок через исполнителя или
  одной строкой в отчёт).

## 6. Merge — строго по одному

Для головы очереди:

1. `scripts/wave.sh budget` ≥ 200 — иначе пауза и отчёт.
2. Отставание: `gh api repos/quantum-soft-dev/data-forge-middleware/compare/<база>...<ветка> --jq .behind_by` > 0
   (соседний PR или чужая сессия уже смержили) → `SendMessage` исполнителю `MODE: REBASE`; после
   `REBASED` — снова пункт 2. Если в `reason` конфликты в коде или перенумерована миграция — повторно
   `review-correctness` (и `review-contracts` для миграции) по diff ребейза.
3. `gh pr checks <pr>` зелёный → `scripts/pr-merge.sh <pr>` — **не** `gh pr merge --delete-branch` (#332):
   код `0` — смержен, ветка удалена; `1` — не смержен; `2` — отказ до действий; `3` — **смержен**, ветка
   осталась: merge не повторять, удалить ветку командой из сообщения.
4. После merge, каждый пункт с проверкой:
   - база `develop`: `gh api repos/quantum-soft-dev/data-forge-middleware/issues/<n> --jq .state` = `closed`;
     иначе закрыть REST (`-X PATCH … -f state=closed -f state_reason=completed`) с комментарием «PR #<pr>
     смержен, `Closes` не сработал». База `migration/<name>`: `Closes` не сработает никогда — закрыть явно
     `` gh issue close <n> --comment 'Merged into `<база>` by #<pr>.' `` (одинарные кавычки);
   - `scripts/board.sh status <n> Done` + сверка (он же снимает все `status: *`),
     `scripts/wave.sh mark <n> Done <pr>`;
   - `scripts/board.sh unblock <n>` — разблокированные в отчёт;
   - родитель (`gh api repos/quantum-soft-dev/data-forge-middleware/issues/<n>/parent`, 404 — нет): в его
     теле `- [ ] #<n>` → `- [x] #<n>` (REST PATCH);
   - `git worktree remove .claude/worktrees/<n>-<slug>` (грязный — оставить и в отчёт),
     `git branch -D <ветка>` (если локальная есть), `git pull --ff-only origin develop`;
   - красный CI базы после merge — стоп волны и вопрос человеку (правило диспетчера).
5. Добор на освободившийся слот (шаг Д).
6. Следующий в очереди — с пункта 1 (он почти наверняка отстал — это ожидаемо).

## Д. Добор — после каждого освобождения слота

Слот освобождается, когда задача журнала уходит из работы: merge → `Done` (шаг 6), `STOPPED` →
`Blocked`/`Ready` и «упал без результата» → `Blocked` (шаг 4), ревью не сошлось за два круга → `Blocked`
(шаг 5), исключение при взятии (шаг 2). `In Review` слот **не** освобождает: задача держит его и свои
ключи до merge.

1. `scripts/wave.sh refill` — те же правила, что `plan`, на свободные слоты; задачи, уже бывшие в
   журнале, не берутся — в том числе новые issues исполнителей этой волны: они ждут следующей. Код 4
   (бюджет ниже порога), «свободных слотов нет» или нет `PICK` — добора нет, волна доводит текущие задачи.
2. Есть `PICK` → те же ручные проверки, что в шаге 1 (зависимость без `Blocked by`, `files?`), затем
   `scripts/wave.sh add <номера PICK>`, взятие каждой по шагу 2 (пункты 1–3) и запуск по шагу 3 — одним
   сообщением на все добранные; в журнале у них заметка `добор`.
3. **Без добора**: человек написал «без добора» (или «доводим волну») — `refill` больше не вызывать до
   конца волны; бюджет упал ниже порога — тоже, пока `wave.sh budget` снова не выше порога.

## H. `health` — проверка здоровья сессий (раз в час по расписанию и по просьбе человека)

1. `scripts/wave.sh health --tasks-dir <каталог задач этой сессии>` (тот, где лежат `<agent-id>.output`
   исполнителей — путь из результата запуска Agent). Строки — `<ВИД>\t<pid|#n>\t<что>\t<что предлагается>`;
   код 1 — есть что убрать.
2. Реакция по видам:
   - `STALE_LOOP`, `STALE_WATCH`, `ORPHAN_SERVER` → `scripts/wave.sh health --tasks-dir <…> --kill`
     (завершает только эти три вида); процессы основной копии, docker, демоны Gradle/Kotlin и чужие
     проекты скрипт не трогает;
   - `STALLED` → `SendMessage` исполнителю: «статус? что делаешь, чего ждёшь»; при следующей проверке снова
     `STALLED` без ответа → как «исполнитель упал» (шаг 4);
   - `CI_RED` → `SendMessage` исполнителю `MODE: FIX` с именами красных проверок;
   - `CI_SLOW` → разовый `gh pr checks <pr>`; ссылку на долгий прогон — в отчёт;
   - `LEFTOVER_WORKTREE` → дочистка шага 6.4.
3. В чат — **только если что-то найдено**: строка на находку, что сделано. `OK` — молча.
4. После `resume` расписание (оно живёт только в сессии) создать заново.

## 7. Завершение волны — в журнале нет задач в работе и последний добор не дал `PICK` (или добор отключён)

1. **Сверка**: `scripts/wave.sh verify`. Каждый `MISMATCH` — один повтор `scripts/board.sh status <n>
   <ожидаемая колонка>` и `verify` ещё раз; осталось — в отчёт как «доску перебивает автоматизация /
   нужен разбор» (на доске 16 включены «Pull request linked to issue» и «Item added to project» — они и
   перебивают).
2. `scripts/board.sh list "In Progress" "In Review"`: карточки не из журнала — показать в отчёте (чужие
   сессии или брошенные — решает человек; признаки брошенной — `ABANDONED` в `scripts/board.sh sweep`),
   не чинить.
3. `scripts/wave.sh health --tasks-dir <…> --kill` — ни одного фонового процесса волны после её конца;
   `CronDelete` расписания; `scripts/wave.sh end`; `git worktree list` — оставшиеся worktree в отчёт.

## 8. Отчёт и стоп

Коротко в чат: таблица «issue | PR | ревью (круги) | итоговая колонка — подтверждена `verify`»
(добранные — с пометкой «добор»); вопросы человеку по остановленным задачам; новые issues с колонкой и
причиной; разблокированные; результат сверки; **превью следующей волны** — PICK-строки
`scripts/wave.sh plan` (он ничего не меняет). Следующую волну **не запускать**.

## R. `resume` — продолжение прерванной волны

`scripts/wave.sh status` и `scripts/wave.sh verify`, затем по каждой незавершённой задаче журнала — по
фактам, а не по памяти:

- `In Progress`, PR нет → новый `task-runner` с `MODE: RESUME` в её worktree (id — в журнал);
- `In Progress`, PR есть и CI зелёный → как `READY_FOR_REVIEW` (шаг 4);
- `In Review` → вердикты из комментария-сводки в PR, если он есть; иначе три ревьюера заново (шаг 5);
- ревью пройдено, PR не смержен → очередь merge (шаг 6);
- смержен, но журнал не `Done` → хвост шага 6.4;
- `Ready` с заметкой `план`/`добор` (дописана, но не взята) → взятие по шагу 2 и запуск по шагу 3.

Затем расписание здоровья заново, `scripts/wave.sh health` сразу (шаг H), добор (шаг Д) и дальше шаги
4–8 как обычно.

**Бюджет GraphQL** (`CLAUDE.md` → «GraphQL budget»): `gh project …` — никогда; всё, что читается через
REST, — через REST; CI — `--interval 60` у исполнителей, у координатора — разовые `gh pr checks`. Остаток —
`scripts/wave.sh budget`; порог волны 1000, merge — 200.
