## User Input

```text
$ARGUMENTS
```

Аргумент — номер issue (можно с `#`, можно голым числом, можно ссылкой на issue).
Если аргумент пуст или не разбирается в номер — остановись и попроси номер, ничего не создавая.

## Назначение

Провести один GitHub issue по всему циклу доставки: статус → ветка и worktree → TDD →
PR → code review до чистого результата → синхронизация с `develop` → **остановка и передача
решения человеку**.

Нормативный источник процесса — **`CLAUDE.md`**, разделы «Development Policy» и «Working from a
GitHub issue». Здесь детализируется механика команд; при расхождении действует `CLAUDE.md`.
`.specify/memory/constitution.md` в этом репозитории — **незаполненный шаблон спек-кита**
(плейсхолдеры `[PRINCIPLE_1_NAME]`), он намеренно не используется: не ссылайся на него и не
принимай его пустые разделы за правила.

## Правила, которые нельзя нарушать

- **Merge в `develop` делает только человек по явной команде.** Дойдя до готовности, ты
  останавливаешься и спрашиваешь. Никогда не мержишь и не пушишь в `develop` сам.
- **Коммит только на зелёных тестах** — гейт из `CLAUDE.md` («Gates summary»), его же
  выполняет `.githooks/pre-commit`. `--no-verify` запрещён политикой.
- **Тесты первыми.** Ни строки продакшн-кода без падающего теста (Rule 2, TDD).
- **Один issue = одна ветка = один PR**, PR мержится **squash**-коммитом в `develop`.
- **Репозиторий строго один** — тот, что в `git config --get remote.origin.url`
  (`quantum-soft-dev/data-forge-middleware`). Ни при каких условиях не трогай другие репозитории.
- Ты можешь создавать ветку, worktree, коммиты, пушить **свою** ветку и открывать PR — это
  часть согласованного процесса. Всё остальное, что меняет общее состояние (merge, закрытие
  issue руками, force-push, удаление чужих веток), требует явного разрешения.

## Статусы: доска и метки

Тикет обязан **пройти всю доску по порядку**, а не прыгать из Backlog сразу в In Review.
Каждый переход — это две записи: колонка на Kanban-доске (её видит человек) и метка в репозитории
(её видно в списке issue и в API).

| Момент | Колонка | Метка |
|---|---|---|
| Заведён, не запланирован | `Backlog` | нет |
| Разобран, критерий готовности сформулирован, не заблокирован | `Ready` | `status: ready` |
| Есть ветка и worktree, идёт работа | `In Progress` | `status: in progress` |
| PR открыт, идёт ревью | `In Review` | `status: in review` |
| Ревью чистое, ветка синхронизирована с `develop`, ждём решения человека | `In Review` | `status: ready to merge` |
| Ждём внешнего решения или зависимости | `Blocked` | `status: blocked` |
| PR смержен, issue закрыт | `Done` | статусные метки сняты |

Отдельной колонки под «ready to merge» на доске нет — карточка остаётся в `In Review`, а
готовность к merge показывает метка.

### Как двигать карточку

Идентификаторы доски — проект, поле `Status`, option-id всех колонок и готовые команды —
лежат **в `CLAUDE.md`, раздел «Board identifiers»**. Это единственный источник; сюда их не
копируй. Дубль в каждой команде разъедется молча, и карточки начнут переезжать в колонку,
которой больше нет.

Карточка ищется по `content.number` == номер issue. Если её на доске нет — добавь
(`gh project item-add`), а не пропускай шаг. Если `item-edit` падает — не выдумывай ID,
перечитай их через `gh project field-list`, как описано там же.

> [!CAUTION]
> **Требуется скоуп `project`.** Если `gh project` отвечает `INSUFFICIENT_SCOPES` — остановись
> и скажи человеку выполнить `gh auth refresh -s project`. Продолжать, обновляя одну метку,
> нельзя: человек смотрит на доску и увидит, что работа не началась.

> [!CAUTION]
> **Проверяй результат, а не факт запуска команды.** После каждого перехода перечитай
> `gh project item-list` и метки. Отработавшая без ошибки команда — не доказательство того,
> что состояние изменилось.

## Шаги

### 1. Прочитать issue и подтвердить рамки

```bash
gh issue view <n> --json number,title,body,labels,milestone,assignees,state,comments
```

- Если issue закрыт — сообщи и остановись.
- Если на нём уже висит `status: in progress` и есть чужой assignee — предупреди и спроси,
  продолжать ли.
- Если метка `question` (решение продукта, а не код) — не заводи ветку. Изложи суть вопроса
  и остановись: такие issue закрываются решением, а не коммитом.
- Кратко перескажи человеку, что понял из issue: симптом, причина, что считается готовым.
  Если в теле issue нет проверяемого критерия готовности — сформулируй его сам и покажи.

### 2. Провести через Backlog → Ready → In Progress

Два отдельных перехода, оба обязательны — «прыжок» из Backlog сразу в работу запрещён.

**2a. Backlog → Ready.** Как только шаг 1 пройден и критерий готовности сформулирован:
колонка `Ready`, метка `status: ready`. Это фиксирует, что тикет разобран и годен к взятию.
Если по ходу разбора выяснилось, что задача заблокирована внешним решением — вместо этого
`Blocked` + `status: blocked`, и остановись.

**2b. Ready → In Progress.** Непосредственно перед созданием ветки:

```bash
gh project item-edit --project-id <project-id> --id <PVTI_...> \
    --field-id <status-field-id> --single-select-option-id <option-id колонки In Progress>
gh issue edit <n> --add-label "status: in progress" --remove-label "status: ready" --add-assignee @me
```

Если у issue нет milestone — поставь текущий спринт (milestone с ближайшей будущей `due_on`;
список: `gh api repos/quantum-soft-dev/data-forge-middleware/milestones`).

Перечитай доску и метки: оба перехода должны быть видны.

### 3. Где работать: изоляция уже может быть готова

**Сначала посмотри, где ты находишься.** Если сессия запущена в Conductor-workspace, изоляция уже
есть — workspace это и есть git-worktree со своей веткой от свежего `origin/develop`:

```bash
echo "$CONDUCTOR_WORKSPACE_PATH"                 # непусто → мы в workspace
git rev-parse --abbrev-ref HEAD                  # ветка workspace'а
git log --oneline origin/develop..HEAD           # пусто → ветка чистая, работа не начиналась
git status --short
```

| Что видишь | Что делать |
|---|---|
| `CONDUCTOR_WORKSPACE_PATH` непуст, ветка чистая | **Работай прямо здесь**, в ветке workspace'а. Никаких вложенных worktree |
| `CONDUCTOR_WORKSPACE_PATH` непуст, но в ветке уже чужая работа (коммиты или незакоммиченное) | Останови и спроси: тут либо другая задача, либо надо создать отдельный workspace |
| Переменной нет (голый клон, `~/projects/data-forge-middleware`) | Создай worktree, как ниже |

**Вложенный worktree внутри Conductor-workspace — ошибка, а не перестраховка.** Диф-вьюер,
Checks-панель и `GetWorkspaceDiff` показывают диф **ветки workspace'а**; работа, спрятанная во
вложенный `.worktrees/…`, для человека в приложении просто не существует.

**Имя ветки.** Conductor уже назвал ветку при создании workspace'а (`plissb/<slug>`) — этого
достаточно: `/merge` находит PR через `gh pr list --head <branch>`, а не по номеру в имени.
**Ветку не переименовывай** без явной просьбы человека. Номер issue живёт в заголовке PR и в
`Closes #<n>` — этого хватает и для связи, и для истории.

Если ветку создаёшь ты сам (голый клон), тип — по метке issue: `bug` → `fix/`,
`enhancement` → `feature/`, иначе `chore/`; слаг — из заголовка (латиница, нижний регистр,
дефисы, 3–5 значащих слов), номер issue в имени: `<type>/<n>-<slug>`. Полноценная фича спек-кита
с каталогом `specs/NNN-name/` — ветка `feature/NNN-name` по Rule 1. Скажи, что выбрал.

```bash
git fetch origin develop
git worktree add .worktrees/<n>-<slug> -b <type>/<n>-<slug> origin/develop
git -C .worktrees/<n>-<slug> config core.hooksPath .githooks
npm --prefix .worktrees/<n>-<slug>/frontend ci        # node_modules гитом не носятся
cp frontend/.env.local .worktrees/<n>-<slug>/frontend/ 2>/dev/null || true
```

Дальше вся работа идёт внутри `.worktrees/<n>-<slug>` — основной каталог не трогаем.
`.worktrees/` в `.gitignore`, а `git worktree prune` висит в archive-скрипте Conductor.

В Conductor-workspace всё это уже сделано за тебя: `.conductor/settings.toml` ставит
`core.hooksPath` и прогоняет `npm --prefix frontend ci`, а `.worktreeinclude` приносит
`frontend/.env.local` и `local-dev/auth0.env`. Если `frontend/node_modules` всё-таки нет —
setup-скрипт не отработал; выполни его руками и скажи об этом, а не обходи фронтовый гейт.

### 4. Спека — по объёму задачи

- **`enhancement`, меняющий контракт или поведение** → полный spec-first по Rule 2:
  `specs/NNN-name/plan.md` и `tasks.md` (`/speckit.plan` → `/speckit.tasks`), номер `NNN` —
  следующий свободный в `specs/`. Крупное изменение дизайна — ещё и `docs/cr-*.md`.
- **`bug` с понятной причиной** → спека не нужна; вместо неё в PR явно опиши причину и
  способ проверки. Задачи веди через TaskCreate/TaskUpdate.

Если issue ссылается на существующий `plan.md` — работай по нему, не плоди новый.

### 5. TDD-цикл

Для каждой задачи: красный тест → минимальная реализация до зелёного → рефактор.
Коммит по завершении задачи, **одним атомарным коммитом на задачу**, только когда зелен
соответствующий гейт. Сообщение коммита — Conventional Commit со ссылкой на issue:
`fix(delta): ... (#<n>)`.

| Что менялось | Гейт перед коммитом |
|---|---|
| Backend (`*.java`, gradle) | `./gradlew test -PexcludeIntegration` |
| Frontend (`frontend/**`) | `cd frontend && npx tsc --noEmit`, `npm --prefix frontend run lint`, `npm --prefix frontend test` |
| И то и другое | оба набора |
| Только docs/specs | ни одного (хук пропускает) |

> [!IMPORTANT]
> **`-PexcludeIntegration` — это «без Testcontainers-сьюта», а не «без Docker».** Около
> тридцати contract-тестов всё равно поднимают PostgreSQL-контейнер. Без запущенного Docker
> гейт падает с невнятной ошибкой внутри `Unsafe.java` — это не твоя правка, это выключенный
> Docker Desktop.

**Перед PR — интеграционный гейт:** `./gradlew integrationTest` (Testcontainers: PostgreSQL +
LocalStack). Он не входит в pre-commit и не запускается в CI на PR — если его пропустить,
интеграционная регрессия обнаружится только на `develop`.

Меняется поведение — правь и удаляй устаревшие тесты, не копи мёртвые (Rule 2, пункт 4).

Отдельно про миграции: Flyway **forward-only**. Никогда не редактируй применённую миграцию,
бери следующий свободный номер `V{N}__description.sql` (текущий максимум смотри в
`src/main/resources/db/migration/`, а не в `CLAUDE.md` — тот может отставать). Для новых
`NOT NULL` колонок — обратимо совместимый `DEFAULT`.

### 6. Документация и журнал изменений

Делается **до открытия PR и в том же PR**, а не «потом отдельно» (Rule 1: недокументированная
фича не merge-ready). Документация, отставшая от кода, вреднее отсутствующей: по ней принимают
решения.

**6a. Журнал изменений.** Живой журнал этого репозитория — раздел **«Recent Changes» в
`CLAUDE.md`**: одна плотная запись на фичу, механизм и последствия, а не пересказ заголовка
коммита. Смотри существующие записи как образец.

`CHANGELOG.md` в корне **намеренно заморожен** — в нём стоит баннер «out of date», он не
обновлялся с v3.0.0 и не покрывает фичи 014–035. Не дописывай в него по своей инициативе и не
пытайся задним числом восстановить; если считаешь, что его пора оживить, — это отдельный тикет
и решение человека.

**6b. Остальное — по тому, что менялось.** Пройди список и для каждого пункта скажи «нужно» или
«не нужно», молча не пропускай:

| Что менялось в коде | Что обновить |
|---|---|
| Поведение или контракт фичи целиком | `docs/cr-<slug>.md` (change request) и/или гайд в `docs/` |
| Публичный REST-контракт, новые эндпоинты, коды ошибок | `CLAUDE.md` (таблицы эндпоинтов), OpenAPI-аннотации, `docs/api-*.md` |
| gRPC: `src/main/proto/delta-ingestion.proto`, номера полей, `ErrorCode` | `docs/delta-v2-wire-contract-answers.md`, `docs/delta-client-v2-guide.md` |
| Клиентский сценарий (Windows-клиент, Bit BI, Parquet Export) | соответствующий `docs/*-client-guide.md` / `*-plugin-guide.md` |
| Схема БД, миграция | запись в `CLAUDE.md` («Recent Changes» + номер следующей миграции) |
| Ключи конфигурации, значения по умолчанию | `README.md` / `application*.yml`-комментарии + `CLAUDE.md` |
| Фронтовые экраны, виджеты, роуты | `docs/ui-base.md`, при необходимости соответствующий `docs/cr-*.md` |
| CI, ветки, гейты, деплой | `README.md`, `docs/cr-tag-driven-dev-deploy.md`, `CLAUDE.md` («Development Policy») |
| Конвенция или факт, нужный будущим сессиям | `CLAUDE.md` |
| Сам процесс доставки | `CLAUDE.md` («Working from a GitHub issue») + эти команды |
| Подход в фиче разошёлся с планом | `specs/NNN-name/plan.md` — переписать, а не оставлять устаревшим |
| Задачи фичи | `specs/NNN-name/tasks.md` — отметить выполненные чекбоксы |

**6c. Проверь себя.** Если в одном документе написано одно, а в другом про то же место другое —
это расхождение, а не мелочь:

```bash
grep -rn "<имя класса, ключ конфига, endpoint>" README.md CLAUDE.md docs/ specs/
```

В отчёте по PR перечисли, какие документы обновлены, а какие сознательно не тронуты и почему.

### 7. PR

```bash
git push -u origin <type>/<n>-<slug>
gh pr create --base develop --title "<тип>(<область>): <суть> (#<n>)" --body-file <файл>
```

Заголовок PR станет заголовком squash-коммита в `develop` — поэтому он обязан быть валидным
Conventional Commit с номером issue, как в существующей истории.

Тело PR: что было сломано, в чём причина, что изменено, как проверить, и строка
`Closes #<n>` — чтобы issue закрылся автоматически при merge.

**In Progress → In Review:** колонка `In Review`, метка `status: in review` вместо
`status: in progress`. Проверь оба перехода.

### 8. Code review до чистого результата

Ревью-цикл — не одна проверка, а петля «ревью → починка → пуш → ревью заново», которая
крутится, пока не станет чисто.

**Что можно закрыть автофиксом, а что нельзя.** Если ревьюер умеет `--fix`, этот режим
разрешён **только для механического класса** находок — там, где правка объективна и решать
нечего:

- форматирование и длина строки; неиспользуемые импорты и переменные; `final` на локальных;
- Java-именование **только для private/local и новых, ещё не опубликованных символов**;
- замена `var` на явный тип (`CLAUDE.md` → Code Style: «Explicit types: avoid `var`») — тип
  проверяет компилятор;
- Javadoc на новых публичных членах — правка чисто добавляющая;
- фронтовый `eslint --fix` в пределах правил форматирования и сортировки импортов: гейт
  `--max-warnings 0` и `tsc --noEmit` ловят ошибку сразу.

**Не механическое в этом репозитории, даже если ревьюер уверенно предлагает** — здесь правка
ломает контракт мимо компилятора и мимо CI:

- переименование поля/компонента record'а в DTO, request/response или JSONB-модели: Jackson
  сериализует **по имени**, клиент ломается молча, тесты остаются зелёными;
- переименование поля JPA-сущности: naming strategy отображает его в имя колонки, и сборка
  этого не заметит;
- `src/main/proto/delta-ingestion.proto` — любые номера полей, имена, значения `ErrorCode`:
  на той стороне уже отгруженный Windows-клиент (см. историю 035 про занятые поля 5 и 7);
- имена метрик Micrometer, кэшей Spring Cache, ключей конфигурации (`@Value`,
  `application*.yml`), заголовков (`X-Plugin-Api-Key`), S3-ключей и путей;
- SQL внутри `@Query`, `@Transactional` (propagation/readOnly), настройки пулов и executor'ов;
- любая правка **применённой** Flyway-миграции;
- фронт: ключи TanStack Query, пути роутов, имена полей Zod-схем и API-DTO.

Общий критерий, по которому проверяется любой будущий кандидат в механический класс: **может ли
правка сломать контракт так, что компилятор и CI этого не заметят?** Если да — она
поведенческая, каким бы правилом стиля ни прикрывалась.

**Всё остальное чинится руками, с решением по каждой находке**: поведение, алгоритм, замысел
теста, текст для оператора, задокументированный инвариант. Ценность петли не в том, что находки
исправлены, а в том, что по каждой *принято решение*, — а автофиксер по умолчанию склоняется к
«починить всё». Правки автофикса проходят тот же гейт коммита и тот же CI, ответный комментарий
по-прежнему отвечает на **каждую** находку, включая закрытые автоматически (`outcome: fixed` +
sha). Границу двигать нельзя: решил, что механический класс надо расширить или сузить, —
остановись и скажи человеку.

**Номер PR всегда подставляй явно.** Если он не назван, действует общее правило «PR текущей
сессии» из `CLAUDE.md` (раздел «The current PR»): выводится из ветки, на которой ты сидишь,
через `gh pr list --head <branch> --state open`. Разрешив номер, передавай его ревьюеру
аргументом — `/code-review <pr>`, а не `/code-review` без аргумента.

**Источники замечаний, все обязательны:**

1. `/code-review <pr>` — плагин `code-review@claude-plugins-official`, основной ревьюер.
   Несколько параллельных агентов (соответствие `CLAUDE.md`, явные баги, git-история изменённого
   кода, комментарии из прошлых PR по этим же файлам), затем отдельная оценка уверенности с
   отсечкой. Результат публикуется **одним итоговым комментарием** к обсуждению PR.

   > [!IMPORTANT]
   > **Плагин одноразовый на PR.** Он прекращает работу, если у PR **уже есть его ревью от
   > прошлого раза**. После пуша исправлений прежний комментарий никуда не денется, поэтому
   > второй прогон, скорее всего, молча ничего не сделает. Не принимай «ничего не произошло»
   > за «замечаний нет».
   >
   > **Проверь, умеет ли твой ревьюер `--fix`.** У плагина из маркетплейса в `allowed-tools`
   > только читающие `gh`-команды и `gh pr comment` — ни Write, ни Edit, то есть `--fix` он не
   > поддерживает и починка целиком наша. Если запускается сборка `/code-review`, принимающая
   > `[low|medium|high|xhigh|max|ultra] [--fix] [--comment] [<target>]`, то `--fix` разрешён в
   > границах механического класса выше. Флага, которого у ревьюера нет, не выдумывай: молча
   > проигнорированный аргумент выглядит как «замечаний не было».

2. Skill `review` на номер PR — **основной ревьюер на втором и последующих кругах**, поскольку
   плагин к тому моменту уже отработал. Его же используй, если плагин недоступен или нужно
   второе мнение по спорному месту.
3. CI — джобы `backend-test` и `frontend-test`: `gh pr checks <pr> --watch --interval 20`.
   Это гейт сборки и тестов, а не ревью. На PR из фичевой ветки джобы `code-quality` и
   `dependency-analysis` **не запускаются** (`run_full_pipeline` включается только для
   `develop`/`release`/`main`) — их отсутствие в списке проверок не сбой.
4. **Комментарии человека на дифе в Conductor** — `GetDiffComments`. Это отдельная поверхность:
   человек оставляет их в панели Changes прямо в приложении, они существуют **ещё до PR**, и в
   `gh` их не видно. Читай их в начале каждого круга и перед выводом «чисто»; они блокируют
   готовность наравне с unresolved-тредами GitHub. Отвечать на них можно там же (`DiffComment`)
   или обычным сообщением человеку — но каждый должен получить решение, как и любая находка.

> [!NOTE]
> **Свои находки до открытия PR публикуй через `DiffComment`, а не в GitHub.** Правило
> Conductor: ревью-фидбек изнутри приложения идёт в панель Checks, в GitHub — только если
> человек прямо попросил. После открытия PR журналом ревью остаётся сам PR: ответы на находки
> ревьюеров публикуются комментарием к PR, как описано ниже.

**GitHub review читается с трёх поверхностей.** `gh pr view <pr> --comments` показывает только
обычные issue comments и **не показывает inline-треды**. Перед выводом «чисто» обязательно прочитай
обычные комментарии, review summaries и следующий GraphQL-срез. Первый вызов не передаёт cursor.
Если `pageInfo.hasNextPage` равен `true`, пагинируй каждое connection независимо: повтори ту же
команду с `-f reviewsCursor=<reviews.endCursor>` или
`-f threadsCursor=<reviewThreads.endCursor>`, накопи новые nodes и продолжай до конца. Второе
connection при этом повторит первую страницу; это допустимый дубль, а не полный результат:

```bash
gh api graphql \
  -f owner=quantum-soft-dev -f name=data-forge-middleware -F number=<pr> \
  -f query='query($owner:String!,$name:String!,$number:Int!,
    $reviewsCursor:String,$threadsCursor:String){
    repository(owner:$owner,name:$name){pullRequest(number:$number){
      reviewDecision
      reviews(first:100,after:$reviewsCursor){
        pageInfo{hasNextPage endCursor}nodes{id author{login} state body url}}
      reviewThreads(first:100,after:$threadsCursor){pageInfo{hasNextPage endCursor}nodes{
        id isResolved isOutdated path line
        comments(first:100){pageInfo{hasNextPage endCursor}nodes{author{login} body url state publishedAt
          pullRequestReview{id state url}}}
      }}
    }}}
  '
```

`comments` — отдельный connection внутри каждого thread. Для каждого thread с
`comments.pageInfo.hasNextPage == true` повторяй следующий запрос с его `id` и
`comments.endCursor`, накапливая nodes до конца:

```bash
gh api graphql \
  -f thread=<PRRT_id> -f commentsCursor=<comments.endCursor> \
  -f query='query($thread:ID!,$commentsCursor:String){
    node(id:$thread){... on PullRequestReviewThread{
      comments(first:100,after:$commentsCursor){
        pageInfo{hasNextPage endCursor}
        nodes{author{login} body url state publishedAt
          pullRequestReview{id state url}}
      }
    }}
  }'
```

Прочитай `body` каждого review summary: `COMMENTED` и `APPROVED` не означают «без находок»,
advisory finding может жить только в summary. Готовность блокирует любой `reviewThread` с
`isResolved == false` — независимо от автора и `isOutdated`; устаревание строки не разрешает
находку. Блокирует любой видимый текущей identity review со `state == PENDING`: его комментарии
ещё черновики. Блокирует текущее `reviewDecision == CHANGES_REQUESTED`; исторический review node
с таким state сам по себе не вечный блокер, решение берётся из `reviewDecision`.

**Закрытие inline-треда — reply → ensure published → resolve**, и после каждой мутации состояние
перечитывается. Ответ добавляется в сам тред:

```bash
gh api graphql \
  -f thread=<PRRT_id> -f body='<ответ с outcome и sha>' \
  -f query='mutation($thread:ID!,$body:String!){
    addPullRequestReviewThreadReply(input:{pullRequestReviewThreadId:$thread,body:$body}){
      comment{url state publishedAt pullRequestReview{id state url}}
    }}'
```

Успех и даже возвращённый URL не доказывают публикацию. Сначала прочитай `comment.state`,
`publishedAt` и `pullRequestReview.state` из ответа:

- review `PENDING` — его `id` надо отправить **до** разрешения треда;
- comment `SUBMITTED` с non-null `publishedAt` и non-`PENDING` review — ответ уже публичен,
  `submitPullRequestReview` повторно не вызывается;
- любое другое сочетание — остановись и перечитай review: публичность не доказана.

Для `PENDING` review:

```bash
gh api graphql \
  -f review=<PRR_id> \
  -f query='mutation($review:ID!){
    submitPullRequestReview(input:{pullRequestReviewId:$review,event:COMMENT}){
      pullRequestReview{id state url}
    }}'

gh api graphql \
  -f thread=<PRRT_id> \
  -f query='mutation($thread:ID!){
    resolveReviewThread(input:{threadId:$thread}){thread{id isResolved}}
  }'
```

После выбранного publication path снова выполни общий read-query и проверь опубликованный ответ,
`PENDING`, `isResolved` и `reviewDecision`. Успешный exit code мутации не является проверкой
результата.

**Петля — это переписка в PR, а не молчаливая работа.** Ревью оставляет замечания
комментарием, ты отвечаешь комментарием о том, что исправлено. Тогда PR сам становится
журналом ревью: видно, что нашли, что сделали и почему что-то не стали делать.

Один круг:

1. Ревьюер публикует замечания комментарием к PR.
2. Чинишь. Коммит только на зелёном гейте, сообщение ссылается на issue.
3. Пушишь.
4. **Публикуешь ответный комментарий** — обязательно, до следующего круга ревью, чтобы
   следующий ревьюер видел, что уже закрыто:

   ```bash
   gh pr comment <pr> --body-file <файл>
   ```

   Формат — по пункту на каждое замечание из предыдущего комментария:

   ```markdown
   ### Исправления по ревью

   1. **<замечание кратко>** — исправлено в `<sha>`: <что именно изменено>.
   2. **<замечание кратко>** — не исправляю: <обоснование>. Вынесено в #<номер нового issue>.
   3. **<замечание кратко>** — не применимо: <почему это ложное срабатывание>.
   4. **<замечание кратко>** — закрыто автофиксом (`outcome: fixed`) в `<sha>`: <что изменено>.
   ```

   Пункт 4 — не поблажка: находка, которую закрыл `--fix`, попадает в комментарий наравне с
   остальными. Иначе часть ревью исчезает из журнала PR именно потому, что прошла гладко.

   Ссылайся на коммит, а не на «поправил выше»: через неделю это единственный способ понять,
   что было сделано. Замечание, которое решено отложить, обязано иметь **свой issue** — по
   правилу «сначала тикет» ниже.

Дальше:

- Повторяй, пока не останется ни одного незакрытого замечания.
- Ни одно замечание не исчезает молча: каждое получает либо исправление, либо обоснованный
  отказ в комментарии.
- Если петля пошла на третий круг и замечания всё те же — остановись и позови человека,
  вместо того чтобы крутиться дальше.

> [!NOTE]
> Красный CI — повод перепрогнать и сверить с `develop`, если тот же тест падает на чистом
> дереве. Это не повод объявить красный прогон «известной флакухой», не проверив, какой
> именно тест упал. Тесты `SqlGenerationService` / `regenerateForBatch` и CONFIG-fallback
> расписания ретенции больше не флакухи — их изолировали в #119; `SqlGenerationIntegrationTest`
> и `BitBiDeltaSqlIntegrationTest` — в #159.

**«Ready to merge» — все четыре условия разом:**

1. Все CI-проверки зелёные, и среди них есть `backend-test` и `frontend-test`.
2. Ни одного незакрытого замечания ни на одной поверхности: нет unresolved `reviewThreads`
   (включая outdated), видимых `PENDING` reviews, текущего `CHANGES_REQUESTED` в
   `reviewDecision` — и ни одного неразобранного комментария из `GetDiffComments`.
3. Ветка синхронизирована с `develop` (шаг 9).
4. `./gradlew test -PexcludeIntegration`, `./gradlew integrationTest` и фронтовые гейты зелёные
   **после** синхронизации, а не до неё.

Пока хоть одно условие не выполнено, метку `status: ready to merge` не ставим.

`/code-review ultra <pr>` — более глубокое облачное ревью — **запускать может только человек**,
оно тарифицируется, и вызвать его самостоятельно нельзя. Если считаешь, что PR того стоит
(широкий диф, правка контракта, чувствительное место), предложи человеку прогнать ultra на
шаге 10 и дождись результата.

### 9. Синхронизация с `develop`

Когда ревью чистое:

```bash
git fetch origin develop
git merge origin/develop
```

- Конфликты — разреши осмысленно, не «беру свою сторону» вслепую. По каждому конфликту
  скажи, что выбрал и почему.
- **Отдельно проверь номер Flyway-миграции.** Текстового конфликта не будет: чужая ветка
  добавила `V49__…`, твоя — тоже, git спокойно возьмёт оба файла, а приложение упадёт на старте.
  После каждой синхронизации пересчитывай `ls src/main/resources/db/migration/` и переименовывай
  свою миграцию на следующий свободный номер (заодно поправь ссылки в доках и тестах).
- После merge прогони гейты заново — разрешённый конфликт мог сломать сборку.
- Запушь; дождись, пока CI снова позеленеет.

Метка `status: ready to merge` вместо `status: in review`. Карточка **остаётся** в `In Review`.

### 10. Остановка и передача решения

Здесь ты **останавливаешься**. Покажи человеку сводку:

- ссылку на PR и его состояние (проверки, ревью);
- что именно изменено, одним абзацем;
- что было в конфликтах при синхронизации, если они были;
- всё, что осталось спорным.

Сводку отправь **сообщением** — её нужно прочитать целиком. И только потом, отдельным ходом,
задай выбор через `AskUserQuestion`: «мержить в `develop`», «доправить», «отложить»
(и «прогнать `/code-review ultra`», если считаешь, что PR того стоит). Кнопки вместо угадывания
по свободному тексту; вариант «Other» приложение добавляет само.
**Merge выполняется только после явного «мержим».**

Услышав «мержим» — запускай `/merge` **без аргумента**: пустой аргумент означает PR текущей
сессии, и он выведется из ветки, на которой ты сидишь.

Тот же `AskUserQuestion` — там, где команда велит остановиться и спросить: спорный конфликт при
синхронизации, issue оказался шире рамок, ветка/worktree заняты чужой работой.

### 11. После merge (только по команде человека)

Сам merge и уборку делает отдельная команда `/merge <pr>` — её запуск человеком и есть
разрешение. Не дублируй её логику здесь и не вызывай `gh pr merge` сам.

Если человек сказал мержить прямо в этом диалоге — выполняй шаги из `/merge`: **squash**
(один issue = один коммит в `develop`, как вся текущая история), затем закрытие issue,
карточка в `Done`, снятие статусных меток и уборка.

Проверь, что issue закрылся по `Closes #<n>`; если нет — закрой явно и скажи об этом.

Уборка зависит от того, где ты работал: вложенный worktree удаляешь сам, а
**Conductor-workspace не трогаешь** — его архивирует человек (или настройка «Auto-archive on PR
close»). Просто скажи, что workspace можно архивировать.

Затем предложи следующий шаг: взять следующий issue из текущего спринта или остановиться.

## Побочные находки: сначала тикет

По ходу работы почти всегда всплывает что-то за рамками issue: мёртвый код, устаревший
документ, подтверждённый TODO, замеченный мимоходом баг, замечание ревью, которое решили
отложить. Порядок действий строгий и обратный привычному:

1. **Сначала ищем, нет ли этого уже.** Обязательный шаг, а не формальность: над репозиторием
   часто работают несколько сессий и workspace'ов параллельно, и одна находка легко
   превращается в три дубля. Ищи **среди открытых и закрытых сразу**:

   ```bash
   gh issue list --state all --search "<ключевые слова>" --limit 30
   gh search issues --repo quantum-soft-dev/data-forge-middleware --state all "<имя класса, файла, ключа конфига>"
   grep -rn "<ключевые слова>" CLAUDE.md docs/
   ```

   Что делать с находками:

   - **Есть открытый issue про то же** — не заводи второй. Добавь в него комментарий с новыми
     данными и, если нужно, подними приоритет. В отчёте скажи, что дополнил существующий тикет.
   - **Есть закрытый issue про то же** — сначала разберись, что это. Либо **регрессия** — тогда
     новый issue со ссылкой «регрессия #<старый>, было исправлено в <sha>, воспроизводится
     снова». Либо твоё наблюдение **устарело**: исправление уже в `develop`, а ты смотришь на
     старый код в своём worktree — тогда тикет не нужен вообще, просто скажи об этом.
   - **Есть запись в `CLAUDE.md` → «Recent Changes» или в `docs/`** — сильный признак, что это
     уже сделано. Проверь код в `origin/develop`, а не только у себя в ветке.
   - **Похоже, но не то же самое** — заводи свой issue и **связывай ссылкой** с найденным.

   Поиск по ключевым словам **находит** эти тикеты: `gh issue list --state all --search
   "SqlGenerationService"` возвращает и #185, и #190, и #200, и #210, а #190 и #200 вдобавок
   начинаются с одних и тех же слов «SQL regeneration». Провал был не в поиске, а в том, что
   **никто не просил его запускать**: #190 и #200 оказались одной работой, невыполнимой ни в
   одном из двух порядков по отдельности, и распутались только потому, что человек за один
   присест прочитал все открытые тикеты, — а этого не требует ни один шаг процесса. Общими у
   них были **файлы**, и список файлов делает эту проверку механической. Поэтому в теле
   нового тикета обязательны три строки (`CLAUDE.md` → «Every follow-up says what it will touch»):
   какие файлы он тронет, нужна ли ему Flyway-миграция **или каталог `specs/NNN-*`**, и какие
   открытые тикеты живут в тех же файлах — **«none found»**, а не «никаких»: у тикетов, заведённых
   до этого правила, файлового списка нет, поэтому ответ ровно настолько хорош, насколько хороша их
   проза.

2. **Только если ничего не нашлось — заводим GitHub issue.** С тем же качеством описания, что
   и любой другой: симптом, причина (если известна), критерий готовности, ссылки на файлы и
   строки, метки (`bug`/`enhancement` + `priority: *`), текущий спринт-milestone. На доске —
   `Backlog`.

   Плюс **три строки про пересечения** (`CLAUDE.md` → «Every follow-up says what it will touch»):
   какие файлы тронет, нужна ли Flyway-миграция или каталог `specs/NNN-*`, и какие открытые тикеты
   живут в тех же файлах. Здесь они перечислены вместе с остальными обязательными полями тела
   намеренно: шаг 1 — это поиск, а спецификация тела — этот шаг, и правило, оставленное только в
   шаге 1, читается как часть поиска и не попадает в issue.
3. **Работу по нему в текущем цикле не начинаем.** Рамки issue не расширяются молча. Скажи
   человеку номер заведённого тикета и предложи взять его следующим (`/github-issue <номер>`)
   или поднять под него отдельный workspace — решение за ним.

Находка без тикета за ней теряется вместе с сессией. Это же правило действует, когда ты решил
не чинить замечание ревью: не «упомянул и забыл», а тикет плюс явное объяснение человеку,
почему отложено.

## Если что-то пошло не так

- Тесты не зеленеют и причина не ясна — не коммить и не обходи хук. Остановись и опиши,
  что видишь.
- Issue оказался шире, чем описан (по ходу выяснились новые причины) — не расширяй молча
  рамки: заведи по этому новый тикет, а текущий доведи в исходных рамках.
- Ветка/worktree с таким именем уже есть — не перезаписывай. Покажи, что нашёл, и спроси.
