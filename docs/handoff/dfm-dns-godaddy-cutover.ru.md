# Инструкция: вернуть `dfm.bitbi.io` из AWS в GoDaddy (зона `bitbi.io`)

> Разовая DNS-операция. Цель: убрать делегацию поддомена `dfm.bitbi.io` на AWS Route53
> и перенести управление записями напрямую в панель GoDaddy домена `bitbi.io`,
> сохранив текущие значения (нулевой даунтайм).
>
> `dev.dfm.bitbi.io` **остаётся на AWS** (по решению от 2026-07-15) — воспроизводим текущие IP.

## Проверенное состояние (сверено напрямую с авторитетных NS)
- Родительская зона `bitbi.io` — на GoDaddy (`ns17/ns18.domaincontrol.com`).
- В ней стоят **4 NS-записи**, делегирующие поддомен `dfm` в AWS Route53 (TTL 3600):
  `ns-905.awsdns-49.net`, `ns-458.awsdns-57.com`, `ns-1274.awsdns-31.org`, `ns-1574.awsdns-04.co.uk`
- Зона Route53 `dfm.bitbi.io` реально содержит **только один хост** — `dev.dfm.bitbi.io` → `100.51.248.92` + `34.199.179.55`. Апекса, MX, TXT, других поддоменов **нет**.
- `test.dfm.bitbi.io` в AWS **не существует** — это **новая** запись на GKE (`136.68.136.183`).

> ⚠️ **Важное уточнение механизма:** в панели GoDaddy отдельную «зону `dfm.bitbi.io`» **не создают**.
> GoDaddy управляет одной плоской зоной `bitbi.io`; поддомены задаются полем **Name (Host)** —
> `dev.dfm`, `test.dfm`. «Создать зону» = убрать делегацию (NS) + добавить A-записи прямо в зону `bitbi.io`.

## 0. Предпосылки
- Доступ к аккаунту GoDaddy, управляющему доменом `bitbi.io` (через admin-контакт).
- Выполнять строго в порядке **Шаг 1 → Шаг 2** (сначала добавить A-записи, затем снять делегацию) — это гарантирует нулевой даунтайм.

## 1. Войти в управление DNS
1. Залогиниться на **godaddy.com** под аккаунтом-владельцем `bitbi.io`.
2. Меню профиля → **My Products** (или **Domain Portfolio**).
3. Найти домен **`bitbi.io`** → кнопка **DNS** (может называться **Manage DNS**).
4. Откроется таблица **DNS Records**.

## 2. ШАГ 1 — добавить A-записи (делать ПЕРВЫМ)
Нажать **Add New Record** для каждой строки и сохранить (**Save**):

| Type | Name (Host) | Value (Points to) | TTL |
|------|-------------|-------------------|-----|
| A | `dev.dfm` | `100.51.248.92` | 600 seconds |
| A | `dev.dfm` | `34.199.179.55` | 600 seconds |
| A | `test.dfm` | `136.68.136.183` | 600 seconds |

Примечания:
- `dev.dfm.bitbi.io` получает **две** A-записи (это нормально — round-robin на AWS ALB).
- TTL рекомендуется поставить **600 с (10 мин)** на время миграции — чтобы потом быстро переназначать. Позже можно поднять до 1 часа.
- Пока делегация (Шаг 2) не снята, эти записи **ещё не работают** — они «ждут». Это безопасно.

## 3. ШАГ 2 — снять делегацию на AWS (делать ВТОРЫМ)
В той же таблице найти **4 записи типа `NS`** с **Name = `dfm`** и **удалить каждую** (значок корзины → **Save**):

```
NS   dfm   ns-905.awsdns-49.net
NS   dfm   ns-458.awsdns-57.com
NS   dfm   ns-1274.awsdns-31.org
NS   dfm   ns-1574.awsdns-04.co.uk
```

> ⚠️ Удалять **только** NS с Name=`dfm`. **Не трогать** NS домена верхнего уровня (`@`) — это неймсерверы самого GoDaddy.

В тот момент, когда эти 4 NS исчезают, зона `bitbi.io` становится авторитетной для `*.dfm.bitbi.io` и начинает отдавать A-записи из Шага 1.

## 4. Проверка (через 5–60 мин, TTL старой делегации = 1 час)
Из любого терминала:
```bash
# 1) делегации на AWS больше нет (пусто = хорошо):
dig +short NS dfm.bitbi.io

# 2) хосты резолвятся на нужные IP:
dig +short A dev.dfm.bitbi.io      # ожидаем 100.51.248.92 и 34.199.179.55
dig +short A test.dfm.bitbi.io     # ожидаем 136.68.136.183

# 3) авторитет — уже GoDaddy, не awsdns:
dig +nssearch dfm.bitbi.io | head
```
Сравнить с публичным резолвером: `dig @8.8.8.8 A test.dfm.bitbi.io`.

## 5. Откат (если что-то пойдёт не так)
Просто **вернуть 4 NS-записи** (Name=`dfm`, значения те же, что в Шаге 2) и удалить добавленные A. Через TTL 1 час авторитет вернётся в AWS Route53. Поэтому **сохраните этот список NS** перед началом.

## Критические предупреждения (прочитать перед выполнением)

1. **TLS не пострадает для `dev.dfm`.** `34.199.179.55` — это AWS ALB с сертификатом `*.dfm.bitbi.io` (ACM, Amazon). Поскольку IP-адрес цели не меняется — HTTPS работает дальше. Изменение только в том, *кто авторитетен по DNS*, а не в цели.

2. **Это РАЗБЛОКИРУЕТ GKE-сертификат для `test.dfm`.** По состоянию репозитория (`k8s/overlays/dev/gateway.yaml`) управляемый Google-сертификат `forge-dev-cert` **не может провизиониться, пока `test.dfm.bitbi.io` не резолвится** на GKE-IP `136.68.136.183`. То есть Шаг 1 (запись `test.dfm`) — фактически предпосылка активации TLS на новом dev-окружении GKE.

3. **`dev.dfm` всё ещё зависит от чужого AWS-аккаунта.** `34.199.179.55` / `100.51.248.92` — это ресурсы в AWS-аккаунте `055383451253` (Quantum Soft), которым вы не управляете. Эта инструкция забирает под ваш контроль **DNS-авторитет**, но **не саму инфраструктуру dev**. Если Quantum Soft выключит этот ALB — `dev.dfm` упадёт. Стратегический финал — после готовности GKE переназначить и `dev.dfm` на GKE-IP (поэтому и рекомендуется TTL 600). Текущие значения воспроизводим только чтобы ничего не сломать во время передачи контроля.

4. **Старая зона Route53 останется «сиротой».** После снятия делегации зона `dfm.bitbi.io` в AWS-аккаунте просто перестанет использоваться (удалить её вы не можете — нет доступа). Это безопасно и ни на что не влияет.

5. **`100.51.248.92`** — необычный адрес; подтверждено, что именно его сейчас отдаёт авторитетный Route53, поэтому воспроизводим как есть. Но стоит отдельно проверить его доступность (`curl -I https://dev.dfm.bitbi.io`), и если трафик идёт только через `34.199.179.55` — вторую запись можно не переносить.
