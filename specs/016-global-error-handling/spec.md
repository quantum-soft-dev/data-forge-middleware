# Feature Specification: Global Error Handling

**Feature Branch**: `016-global-error-handling`
**Created**: 2026-01-11
**Status**: Draft
**Input**: User description: "API для глобального сохранения ошибок, не связанных с Batch. Клиент рапортует об ошибках уровня приложения (отсутствие файловой системы, невозможность запуска). На UI ошибки отображаются глобально в Dashboard с возможностью отметить как прочитанные."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Report Global Error from Client (Priority: P1)

Клиентское приложение (Data Forge Client) обнаруживает критическую ошибку уровня системы, которая не связана с конкретным batch-процессом. Это может быть: отсутствие доступа к файловой системе, невозможность запуска приложения, ошибка конфигурации, сбой сетевого соединения до начала batch и т.д. Клиент отправляет информацию об ошибке на сервер для последующего анализа и отображения пользователю.

**Why this priority**: Без возможности сообщить о глобальных ошибках пользователи не узнают о проблемах с клиентским приложением, пока не проверят логи локально. Это критический функционал для мониторинга здоровья системы.

**Independent Test**: Можно полностью протестировать отправкой POST запроса с данными ошибки и проверкой записи в базе данных. Доставляет ценность — ошибки начинают накапливаться и могут быть проанализированы.

**Acceptance Scenarios**:

1. **Given** клиент авторизован с валидным JWT токеном, **When** клиент отправляет глобальную ошибку с типом, сообщением и метаданными, **Then** ошибка сохраняется с привязкой к site_id клиента и batchId = null
2. **Given** клиент авторизован, **When** клиент отправляет ошибку с опциональным severity уровнем, **Then** severity сохраняется (по умолчанию ERROR если не указан)
3. **Given** клиент не авторизован (невалидный токен), **When** клиент пытается отправить ошибку, **Then** возвращается 401 Unauthorized

---

### User Story 2 - View Global Errors on Dashboard (Priority: P1)

Пользователь (владелец аккаунта) входит в Dashboard и видит секцию/виджет с глобальными ошибками от его клиентских приложений. Ошибки отсортированы по времени (новые сверху). Пользователь видит непрочитанные ошибки выделенными, может просмотреть детали и отметить как прочитанные.

**Why this priority**: Без отображения на UI вся функциональность сбора ошибок бесполезна. Пользователь должен узнавать о проблемах своих клиентов.

**Independent Test**: Можно протестировать создав несколько глобальных ошибок через API, затем открыв Dashboard и проверив их отображение. Доставляет полную пользовательскую ценность.

**Acceptance Scenarios**:

1. **Given** у аккаунта есть 5 глобальных ошибок (3 непрочитанных), **When** пользователь открывает Dashboard, **Then** отображается виджет с ошибками, непрочитанные визуально выделены, сортировка от новых к старым
2. **Given** пользователь видит список ошибок, **When** пользователь выбирает ошибку, **Then** отображаются полные детали: тип, сообщение, время, site, severity, metadata
3. **Given** пользователь просматривает непрочитанную ошибку, **When** пользователь нажимает "Mark as Read", **Then** ошибка помечается как прочитанная, визуальное выделение снимается

---

### User Story 3 - Mark Multiple Errors as Read (Priority: P2)

Пользователь хочет быстро отметить несколько ошибок как прочитанные без необходимости кликать на каждую по отдельности. Это полезно после массового просмотра ошибок или для очистки списка от старых уведомлений.

**Why this priority**: Улучшает user experience, но основной функционал работает и без этого. Можно реализовать после P1.

**Independent Test**: Можно протестировать выбрав несколько ошибок и применив массовое действие. Требует наличия P1 функционала.

**Acceptance Scenarios**:

1. **Given** у пользователя есть 10 непрочитанных ошибок, **When** пользователь выбирает 5 ошибок и нажимает "Mark Selected as Read", **Then** все 5 ошибок помечаются как прочитанные
2. **Given** пользователь на странице ошибок, **When** пользователь нажимает "Mark All as Read", **Then** все непрочитанные ошибки текущего фильтра помечаются как прочитанные

---

### User Story 4 - Unread Errors Counter Badge (Priority: P2)

Пользователь видит на Dashboard виджете Global Errors индикатор (badge) с количеством непрочитанных глобальных ошибок. Это позволяет быстро понять, требуется ли внимание.

**Why this priority**: Повышает видимость проблем, но Dashboard уже показывает список ошибок. Дополнительное удобство.

**Independent Test**: Можно протестировать проверкой отображения счётчика и его обновления при появлении новых ошибок или маркировке как прочитанных.

**Acceptance Scenarios**:

1. **Given** у пользователя 7 непрочитанных глобальных ошибок, **When** пользователь открывает Dashboard, **Then** виджет Global Errors отображает badge "7"
2. **Given** badge показывает "3", **When** пользователь отмечает одну ошибку как прочитанную, **Then** badge обновляется до "2"
3. **Given** все ошибки прочитаны, **When** клиент отправляет новую ошибку, **Then** badge появляется со значением "1"

---

### Edge Cases

- Что происходит если клиент отправляет ошибку с очень длинным сообщением? — Сообщение обрезается до максимально допустимой длины (10,000 символов)
- Что происходит если метаданные превышают лимит? — Возвращается 400 Bad Request с описанием ошибки
- Как система обрабатывает большой объём ошибок от одного клиента? — Ошибки сохраняются без rate limiting, но UI использует пагинацию
- Что если site был деактивирован после отправки ошибок? — Ошибки остаются в системе, привязаны к site_id, отображаются в истории
- Как работает статус "прочитано" при нескольких пользователях одного аккаунта? — Статус прочитанности общий для аккаунта (не per-user)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА принимать глобальные ошибки от клиентов через API endpoint без обязательной привязки к batch
- **FR-002**: Система ДОЛЖНА сохранять следующие атрибуты глобальной ошибки: тип, заголовок, сообщение, severity, метаданные, время возникновения, версия клиента
- **FR-003**: Система ДОЛЖНА поддерживать уровни severity: CRITICAL, ERROR, WARNING, INFO (по умолчанию ERROR)
- **FR-004**: Система ДОЛЖНА автоматически помечать новые ошибки как "непрочитанные"
- **FR-005**: Пользователи ДОЛЖНЫ иметь возможность отметить ошибку как "прочитанную"
- **FR-006**: Пользователи ДОЛЖНЫ иметь возможность отметить несколько ошибок как "прочитанные" одним действием
- **FR-007**: Система ДОЛЖНА отображать глобальные ошибки на Dashboard в отдельном виджете/секции
- **FR-008**: Система ДОЛЖНА сортировать ошибки по времени возникновения в порядке убывания (новые сверху)
- **FR-009**: Система ДОЛЖНА визуально выделять непрочитанные ошибки в списке
- **FR-010**: Система ДОЛЖНА отображать счётчик непрочитанных ошибок
- **FR-011**: Система ДОЛЖНА поддерживать пагинацию списка ошибок
- **FR-012**: Система ДОЛЖНА разрешать просмотр глобальных ошибок только владельцу аккаунта, к которому принадлежит site

### Key Entities *(include if feature involves data)*

- **ErrorLog (расширенная)**: Существующая сущность error_logs расширяется двумя новыми полями:
  - `severity` (enum: CRITICAL, ERROR, WARNING, INFO) — уровень критичности ошибки
  - `is_read` (boolean, default false) — статус прочтения для аккаунта
  - Глобальные ошибки отличаются от batch-ошибок значением `batch_id = NULL`
  - Связь: принадлежит Site (many-to-one), опционально связана с Batch
  - Миграция: существующие записи получают severity=ERROR, is_read=true

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Клиентское приложение может отправить глобальную ошибку и получить подтверждение в течение 2 секунд при нормальных сетевых условиях
- **SC-002**: Пользователь видит новую глобальную ошибку на Dashboard без необходимости обновлять страницу (при следующем визите или через polling)
- **SC-003**: Пользователь может отметить 100 ошибок как прочитанные одним действием за время менее 3 секунд
- **SC-004**: Система корректно отображает и позволяет управлять 10,000+ ошибками на аккаунт без деградации производительности UI (пагинация по 20-50 элементов)
- **SC-005**: Счётчик непрочитанных ошибок обновляется в течение 5 секунд после изменения статуса
- **SC-006**: 100% глобальных ошибок от клиентов сохраняются в системе без потерь

## Assumptions

- **TDD обязателен**: Тесты (contract tests, integration tests, unit tests) пишутся ПЕРЕД имплементацией для backend (JUnit 5) и frontend (Vitest)
- Статус "прочитано" является общим для всего аккаунта, а не per-user (все пользователи аккаунта видят одинаковый статус)
- Глобальные ошибки хранятся в существующей таблице error_logs (расширенной новыми полями severity, is_read), используя готовую инфраструктуру партиционирования
- Retention policy для глобальных ошибок такой же как для batch-ошибок (24 месяца)
- Frontend использует polling для обновления списка ошибок (real-time WebSocket out of scope)
- Severity уровни используются только для визуального отображения (фильтрация — опционально в будущем)

## Clarifications

### Session 2026-01-11

- Q: Стратегия хранения данных — расширить error_logs или создать отдельную таблицу? → A: Расширить существующую таблицу error_logs новыми полями (isRead, severity)
- Q: Как обрабатывать существующие ошибки при миграции? → A: Существующие ошибки получают severity=ERROR, is_read=true (считаются прочитанными)
- Q: Где размещать badge с количеством непрочитанных ошибок? → A: Только на Dashboard виджете Global Errors
- Q: Использовать ли TDD подход? → A: TDD обязателен для backend (JUnit 5) и frontend (Vitest) — тесты пишутся ПЕРЕД имплементацией

## Out of Scope

- Real-time уведомления (WebSocket/SSE) о новых ошибках
- Email/SMS/Push уведомления о критических ошибках
- Per-user статус прочтения (у каждого пользователя свой статус)
- Автоматическая агрегация/дедупликация похожих ошибок
- Rate limiting для отправки ошибок
- Экспорт глобальных ошибок в CSV/файл
- Фильтрация ошибок по severity/type/site на UI (может быть добавлено позже)
