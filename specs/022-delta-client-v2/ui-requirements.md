# UI Requirements — Delta Client v2 (022): Sync Monitoring & Management

**Назначение документа**: техническое задание для Cloud Designer на новый экран/раздел фронтенда, отражающий данные и статус ingestion-протокола Delta Client v2 (gRPC changelog + checkpoints). Документ не про транспорт/бэкенд-логику — та уже реализована (см. [plan.md](./plan.md), [SESSION-HANDOFF.md](./SESSION-HANDOFF.md), [docs/cr-delta-client-v2.md](../../docs/cr-delta-client-v2.md)) — а про то, что и как должно быть видно и управляемо пользователем/админом.

**Задача дизайну — явный запрос на переосмысление, а не косметику.** Существующие экраны продукта (Batch List / Batch Detail / Site List, см. `frontend/src/features/upload-history`, `frontend/src/widgets/site-list`) построены на голых Tailwind-таблицах и карточках-«dl» без единого визуального языка для операционного мониторинга. Для Delta Sync — это принципиально другой тип данных: не список файлов, а **живое состояние потока** (watermark, лаг, ряд чекпойнтов по времени, серии сегментов). Механически повторить паттерн Batch Detail («карточка с dt/dd + плоская таблица») здесь означает унаследовать ту же неоптимальность, а не решить её.

**Поэтому цель этого ТЗ — не описать готовый макет, а дать дизайну данные, роли и ограничения, на основе которых Cloud Designer предлагает новый визуальный язык** (компоновка, иерархия, использование цвета/графиков/таймлайнов для операционных метрик) и раскладку экрана. Раздел §8 ниже переформулирован как бриф для дизайна, а не как список готовых Tailwind-классов.

**Статус источника данных**: часть данных уже отдаётся существующими REST-эндпоинтами (см. §5). Часть UI-функций требует новых backend-эндпоинтов, которых сегодня нет — они явно помечены в §6 и §7 как "Backend TODO". Frontend сегодня (`frontend/src/`) вообще не знает о `SiteType`, `ClientApiVersion` или Delta-сущностях — это полностью новая поверхность.

---

## 1. Контекст

- Delta v2 — альтернативный (не файловый) протокол загрузки данных клиентом: вместо полных CSV-снапшотов клиент шлёт changelog (вставки/обновления/удаления) по gRPC. Сервер хранит его как **сегменты changelog** (`changelog_segments`) и периодически материализует **чекпоинты** (`checkpoints`) — снапшот на таблицу — плюс отслеживает watermark синхронизации (`site_sync_state`).
- Сайт либо `ClientApiVersion.V1` (старый HTTP `/api/dfc`, полные снапшоты), либо `V2` (Delta gRPC). Это отдельное измерение от `SiteType` (`DBF` / `POSTGRES_CDC`).
- Сегодня в личном кабинете (Dashboard → Upload History → Batch Detail) пользователь видит список файлов батча. Для Delta v2 сайтов "файлов" нет (`uploaded_files` пуст) — вместо этого есть **per-table insert/update/delete counts** (`deltaStats`, уже добавлено в `BatchDetailDto`, T6.3), которые сегодня **не отображаются нигде во фронтенде**.
- Кроме истории отдельных батчей, нет никакого способа посмотреть **текущее состояние синхронизации сайта**: насколько клиент отстаёт (lag), когда был последний чекпоинт, сколько строк в каждой таблице, не завис ли клиент.

## 2. Пользователи и доступ

| Роль | Что видит |
|---|---|
| **Regular User (ROLE_USER)**, владелец аккаунта | Delta-статистику и статус синхронизации **только для своих сайтов** (Dashboard → Site detail / Upload History). Доступ к своим данным read-only + ограниченные действия (см. §6.3 "Force re-baseline"). |
| **Admin (ROLE_ADMIN)** | То же самое для **любого** сайта/аккаунта из Admin-панели, плюс операционные действия (форсировать чекпоинт, посмотреть сырые сегменты, retention). |

Видимость раздела **обусловлена типом сайта**: раздел показывается только если `site.clientApiVersion === 'V2'`. Для V1-сайтов раздел скрыт полностью (не "пусто", а отсутствует в навигации/табах).

## 3. Scope

**В рамках:**
1. Отображение per-table delta-статистики в существующей странице деталей батча (Batch Detail).
2. Новый виджет/вкладка **"Delta Sync"** на странице сайта (site detail) — просмотр текущего состояния синхронизации, чекпоинтов, последних сегментов.
3. Минимальный набор управляющих действий: форс пересборки чекпоинта, инициировать re-baseline (полный снапшот при следующем подключении клиента), скачать текущий CSV/Parquet чекпоинт.
4. Индикация "здоровья" синхронизации (лаг, давность последнего коммита) в списке сайтов (`SiteList`) — компактный бейдж, не отдельный экран.

**Вне рамок (out of scope) — явно не делать:**
- Никакого live-стриминга/визуализации самого gRPC-трафика в реальном времени (WebSocket подписки на сессии) — только polling обычных REST-эндпоинтов, как везде в проекте.
- Редактирование `site_schemas` из этого раздела (это отдельный существующий флоу — schema upload).
- Просмотр содержимого changelog-сегментов построчно (это сырые protobuf-файлы в S3; не для конечного пользователя).
- Управление `POSTGRES_CDC` vs `DBF` (SiteType) — не путать с `ClientApiVersion`, это разные оси, `SiteType` уже управляется в существующем UI создания сайта.

## 5. Экран 1 — Delta Stats в Batch Detail (данные уже есть)

**Backend**: `GET /api/v1/account/batches/{batchId}` (и admin-эквивалент) уже возвращает `BatchDetailDto.deltaStats: DeltaTableStatsDto[]` — `{ table, inserts, updates, deletes }`. Пусто (`[]`) для v1-батчей.

**Требование**: в [BatchDetailView.tsx](../../frontend/src/features/upload-history/ui/BatchDetailView.tsx) добавить блок:

- Если `batch.deltaStats.length > 0`:
  - Скрыть/не показывать секцию "Files" (список файлов) и `FileTable` — для Delta-батчей файлов нет.
  - Показать таблицу **"Table Changes"**: колонки `Table | Inserted | Updated | Deleted | Total`, строка **Total** внизу (сумма по всем таблицам). Сортировка по имени таблицы (уже приходит отсортированной с бэка, но не полагаться на порядок).
  - Иконки/цвета: inserts — зелёный, updates — синий/жёлтый, deletes — красный (согласовать с существующей цветовой схемой status-бейджей в этом же файле).
  - Кнопки Download/Excel/Compare (сегодня рассчитанные на файлы) — скрыть для Delta-батчей, т.к. нет `uploaded_files`.
- Если `batch.deltaStats.length === 0` и `batch.files.length === 0` (Delta-батч без изменений, например пустая CONTINUOUS-сессия) — показать пустое состояние "No changes in this session" вместо пустой таблицы файлов.
- Если `batch.deltaStats.length === 0` и `files.length > 0` — текущее поведение (v1-батч) не меняется.

## 6. Экран 2 — вкладка "Delta Sync" на странице сайта

Показывается только для сайтов с `clientApiVersion === 'V2'`.

**Важно**: подразделы 6.1–6.3 ниже перечисляют **данные, действия и поля**, которые должны присутствовать на экране — это контракт по содержанию, не по форме. Компоновка (карточка/таймлайн/шкала/что угодно ещё) — предмет дизайн-брифа §8; таблицы в этом разделе — способ перечислить поля, а не обязательный layout.

### 6.1 Sync State Card (обзор, всегда виден)

Поля (из `site_sync_state`, нужен новый эндпоинт — см. §7):

| Поле | Источник | Отображение |
|---|---|---|
| Последний применённый seq (`lastAppliedSeq`) | `site_sync_state.last_applied_seq` | число |
| Последний чекпоинт seq / время (`lastCheckpointSeq` / `lastCheckpointAt`) | `site_sync_state` | число + относительное время ("2 часа назад") |
| **Lag** = `lastAppliedSeq - lastCheckpointSeq` | вычисляется на фронте или бэке | число + цветовой индикатор (зелёный < N, жёлтый, красный — пороги обсудить с продуктом, дефолт: жёлтый > 1000, красный > 10000 несмачекпоинченных записей) |
| Версия схемы (`schemaVersion`) | `site_sync_state.schema_version` | число, ссылка на существующий Schema Viewer, если есть |
| Последнее обновление (`updatedAt`) | `site_sync_state.updated_at` | относительное время; если > 24ч и сайт активен — предупреждающий бейдж "Sync stalled?" |

Пустое состояние: если для сайта ещё нет строки `site_sync_state` (клиент ни разу не подключался) — карточка показывает "No sync activity yet" вместо нулей.

### 6.2 Checkpoints Table (по таблицам)

Список чекпойнтов сайта (`checkpoints`, одна строка на таблицу):

| Table | Seq | Row Count | Last Updated | Files |
|---|---|---|---|---|
| orders | 4821 | 1 204 500 | 3 hours ago | CSV · Parquet |

- Колонка "Files" — иконки-ссылки скачивания, если `s3KeyCsv`/`s3KeyParquet` не null (presigned URL, 15 мин — как везде в проекте, см. паттерн S3 presigned URLs). Если оба null — прочерк.
- Сортировка по умолчанию: по имени таблицы.
- Клик по строке — не обязателен (без drill-down в MVP).

### 6.3 Управляющие действия

| Действие | Кому доступно | Поведение |
|---|---|---|
| **Force checkpoint rebuild** | Admin | Кнопка "Rebuild checkpoint now" — ставит задачу пересборки чекпоинта вне расписания `CheckpointScheduler`. Подтверждающий диалог (может быть тяжёлой операцией). После — тост "Checkpoint rebuild scheduled" + инвалидация кэша Sync State/Checkpoints. |
| **Request re-baseline** | Admin, и Owner-пользователь (с подтверждением) | Кнопка "Request full re-baseline" — помечает сайт так, что при следующем подключении клиент получит `action=FULL_SNAPSHOT` вместо инкрементального дельта-потока (переиспользует существующую server-side логику ре-baseline, см. CR §9 "re-baseline"). Подтверждающий диалог с явным предупреждением: "Client will re-send a full snapshot on next connect; this may take a while for large datasets." Это **необратимо запускаемое** действие с видимым эффектом у клиента — обязательно modal-confirmation, не единичный клик. |
| **View recent segments** | Admin | Разворачиваемая таблица последних N (например 20) `changelog_segments` для сайта: `firstSeq–lastSeq | recordCount | mode (DELTA/FULL_SNAPSHOT/CONTINUOUS) | createdAt`. Не отдельная страница — collapsible-секция внутри вкладки. |

Owner-пользователю (не admin) в MVP **не** показывать "Force checkpoint rebuild" и "View recent segments" — это операционные/отладочные действия. Owner видит только Sync State Card, Checkpoints Table (read-only) и, опционально, кнопку re-baseline своего же сайта.

### 6.4 Состояния

- **Loading**: skeleton-карточки, консистентно с остальным приложением (см. `Loader2` спиннер в `BatchDetailView`).
- **Error**: если API вернул ошибку — стандартный error-блок (см. паттерн `rounded-lg border border-red-200 bg-red-50` в `BatchDetailView.tsx:93`).
- **Not applicable**: если сайт `clientApiVersion === 'V1'` — вкладка отсутствует в навигации (не "серая"/disabled, а не рендерится).

## 7. Backend TODO — новые эндпоинты, нужные под этот UI

Сегодня `site_sync_state`, `checkpoints`, `changelog_segments` **не имеют HTTP-презентации** — только внутреннее использование gRPC-сервисом ingestion'а. Для UI нужны (namespace по аналогии с существующими `/api/v1/account/**` и `/api/v1/admin/**`):

| Эндпоинт | Метод | Что отдаёт |
|---|---|---|
| `/api/v1/account/sites/{siteId}/delta/sync-state` (+ admin вариант `/api/v1/admin/sites/{siteId}/delta/sync-state`) | GET | Проекция `SiteSyncState` → DTO для §6.1 |
| `.../delta/checkpoints` | GET | Список `Checkpoint` по сайту (+ presigned URL для CSV/Parquet, генерируемые по требованию, не хранить голые S3 keys в ответе) |
| `.../delta/segments?limit=20` | GET (admin only) | Последние `ChangelogSegment` по сайту, отсортированные по `createdAt desc` |
| `.../delta/checkpoints/rebuild` | POST (admin only) | Форсирует пересборку чекпоинта вне расписания |
| `.../delta/rebaseline` | POST (admin + owner) | Помечает сайт на `FULL_SNAPSHOT` при следующем подключении (реализация уже существует внутри `DeltaIngestionService`/reconciliation — нужно завести публичный триггер) |

Эти эндпоинты — **предпосылка** для реализации UI из §6; без них можно сделать только Экран 1 (§5), т.к. `deltaStats` уже приходит с бэкенда. Порядок работы: сначала backend-задачи (новая ветка, следующая свободная миграция при необходимости — сейчас нет новых таблиц, только чтение существующих, миграция не нужна), затем frontend.

## 8. Дизайн-бриф для Cloud Designer (новый визуальный язык)

Это не список готовых компонентов, а вводные, на основе которых нужно **предложить** визуальный язык и компоновку экрана. Ожидаемый результат — макет/визуальная концепция (не обязательно финальный код), которую затем реализуют поверх React + Tailwind + shadcn/ui.

### 8.1 Природа данных — то, что должно определить форму, а не наоборот
- **Состояние потока, не список записей.** Ключевая метрика — лаг (`lastAppliedSeq − lastCheckpointSeq`) — это *расстояние между двумя постоянно двигающимися указателями*, а не статичное число в `dt/dd`. Форма отображения должна дать это почувствовать: например положение на шкале/градиенте между «checkpoint» и «applied», а не просто цифра рядом с подписью.
- **Временной ряд, а не снимок.** У сайта есть история чекпойнтов и сегментов во времени — потенциал для мини-таймлайна/спарклайна (частота коммитов, размер сегментов, всплески лага), а не только «последнее значение».
- **Многотабличность.** Один сайт = N таблиц, у каждой свой `rowCount`/`seq`/файлы. Плоская таблица работает, но стоит рассмотреть более компактные представления (напр. сгруппированные карточки с относительным размером/весом таблицы, а не только строки-цифры) — предложить и обосновать выбор.
- **Операционная срочность.** Есть состояния, требующие внимания (лаг растёт, checkpoint не строился давно, resume/reconciliation failures) — они должны быть визуально выделены сильнее, чем обычные информационные поля, а не спрятаны в общий серый текст, как сейчас в Batch Detail.

### 8.2 Что не менять (ограничения, не предмет дизайна)
- Стек: React 19 + TypeScript + Tailwind + shadcn/ui примитивы как база компонентов; TanStack Query для данных; Zod-схемы для DTO.
- Структура кода по FSD (см. CLAUDE.md): `features/delta-sync/{api,model,ui}` + `widgets/delta-sync/DeltaSyncWidget.tsx` с проп `canManage: boolean`.
- Экран встраивается в существующий каркас приложения (шапка, навигация, вкладки сайта) — редизайн ограничен содержимым вкладки "Delta Sync", не глобальным shell'ом продукта.
- Confirmation-действия (rebuild/rebaseline) — модальные диалоги, не `window.confirm`.
- Polling живых метрик (лаг может меняться во время активной сессии) — `refetchInterval` через TanStack Query, разумный интервал (ориентир 15–30s), без WebSocket/стриминга (см. §3 out of scope).

### 8.3 Открытые вопросы к дизайну
- Нужен ли отдельный визуальный язык (палитра/иконография) для "операционных/мониторинговых" экранов продукта в целом, который потом можно переиспользовать для других будущих мониторинговых поверхностей (например метрик Bit BI плагина), или это разовое решение только для Delta Sync?
- Пороговые значения лага (§6.1: жёлтый/красный) — предложить не только цвета, но и то, как визуально показать "насколько" плохо (например прогресс-бар/градиентная шкала вместо жёсткого badge с текстом).
- Сегодня статус-бейджи проекта используют плоскую палитру `green/yellow/red/blue-100/800` (см. `BatchDetailView.tsx`) — решить, наследовать её ради консистентности с остальным продуктом или предложить новую, более выразительную систему именно для операционных индикаторов (с обоснованием trade-off "консистентность vs. выразительность").

## 9. Нефункциональные требования

- Все суммы/счётчики — потенциально большие числа (сотни тысяч–миллионы строк): форматировать с разделителями разрядов (переиспользовать `formatters` из `shared/lib/formatters`, как `formatBytes`/`formatDateTime`).
- Локаль: проект не мультиязычный сегодня (тексты на английском в UI, как в `BatchDetailView.tsx`) — новые тексты тоже на английском, несмотря на то что этот документ требований на русском.
- Presigned URL для скачивания чекпоинтов — не кэшировать дольше их TTL (15 мин, как везде в проекте); повторный клик после истечения должен просто запросить новый.
- Confirmation для re-baseline и rebuild — через shadcn `AlertDialog`/`Dialog`, не `window.confirm`.

1. Экран 1 (§5): Delta-статистика видна в Batch Detail для V2-сайтов, файловый UI скрыт для них, юнит-тесты компонента (Vitest + RTL) покрывают три состояния (deltaStats non-empty / both empty / files present).
2. Экран 2 (§6): вкладка "Delta Sync" видна только для V2-сайтов, реализована по согласованной в п.0 концепции, показывает Sync State + Checkpoints; управляющие действия — за флагом `canManage`/ролью; все действия имеют confirmation и invalidate соответствующих queries после успеха.
