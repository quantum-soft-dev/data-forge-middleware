# Delta Client v2 — архитектура интеграции и вопросы клиенту

> Документ для команды клиента (C#/.NET). Описывает, как устроена интеграция, что
> фиксировано сервером (data-forge-middleware) и что разрабатывает клиент, плюс
> список вопросов, на которые нужны ответы, чтобы зафиксировать контракт.
>
> Имена RPC/полей/enum'ов — из gRPC-контракта (`src/main/proto/delta-ingestion.proto`),
> они фиксированы и приведены на английском как есть.

## 1. Общая схема (кто что делает)

```
┌────────────────────────────┐         gRPC :9090 (HTTP/2)        ┌────────────────────────────────┐
│  Клиент (C#/.NET)          │  ── StreamChanges / GetSyncState ─▶ │  Server: data-forge-middleware   │
│                            │       SubmitSchema                  │                                  │
│  • CDC из источника        │                                     │  • аутентификация (HTTP :8080)   │
│  • нормализация в          │  ◀── SessionOpened / Ack /          │  • валидация (seq, схема,        │
│    ChangeRecord            │       SessionCommitted / Error      │    reconcile)                    │
│  • генерация seq           │                                     │  • changelog → S3 (bronze)       │
│  • управление сессиями     │  ── HTTP :8080 ──▶ /api/v1/device/* │  • checkpoint → CSV (Bit BI) +   │
│  • auth + refresh          │      (токен)                        │    Parquet (Power BI)            │
└────────────────────────────┘                                     └────────────────────────────────┘
```

### Server предоставляет (фиксировано, клиент только потребляет)
- gRPC-сервис `DeltaIngestion` на **:9090**: `GetSyncState`, `SubmitSchema`, `StreamChanges`.
- Выдачу токенов по HTTP на **:8080** (`/api/v1/device/**`).
- Приём изменений, проверку `seq`/схемы/сверки, персист changelog-сегментов в S3, watermark
  (`last_applied_seq`) на сайт, периодические checkpoint'ы и реконструкцию снапшотов.
- Логику восстановления: ответы `PROCEED` / `RESUME_FROM` / `NEED_REBASELINE`.

### Client разрабатывает
1. **Захват изменений** из источника (CDC) и приведение к `ChangeRecord`.
2. **Генерация `seq`** — на сайт, монотонно возрастающая, без пропусков, **переживает рестарт клиента**.
3. **Схема**: определение колонок/типов/PK, вызов `SubmitSchema` при изменении структуры.
4. **Типизация значений**: маппинг типов источника → PG-типы + типизированные `Value`
   (различение NULL и «поле отсутствует»).
5. **Управление сессиями**: выбор режима (`DELTA` / `FULL_SNAPSHOT` / `CONTINUOUS`), батчинг,
   `client_session_id`, обработка `Ack`/`SessionCommitted`.
6. **Аутентификация**: device flow + refresh, токен **на каждый сайт**.
7. **Восстановление**: gap → re-baseline, `RESUME_FROM`, реконсиляция на `SessionEnd`.
8. **Бутстрап**: первичная полная загрузка как `FULL_SNAPSHOT`.

## 2. Контракт (что фиксировано сервером)

### 2.1 Транспорт и аутентификация
- gRPC поверх HTTP/2. **Сейчас plaintext (без TLS)** — см. вопрос N1.
- На каждом вызове — метаданные `authorization: Bearer <access_token>`. Без токена → `UNAUTHENTICATED`.
- Токен — HMAC-JWT с зашитыми `siteId`/`accountId`. **Один токен = один сайт.**
- Токен получается через Auth V2 Device Flow по HTTP:
  `POST /api/v1/device/authorize` → подтверждение на `/api/v1/device/verify` →
  поллинг `POST /api/v1/device/token` → `access_token` + `refresh_token`;
  обновление — `POST /api/v1/device/auth/refresh`.
  (Есть упрощённый deprecated-путь: `POST /api/v1/device/auth/token` с Basic `domain:clientSecret`.)
- Интерцептор проверяет токен **в момент открытия вызова**, не継続но: уже открытый `StreamChanges`
  переживёт истечение токена, но новый вызов/reconnect требует валидного токена.

### 2.2 RPC
| RPC | Тип | Назначение |
|---|---|---|
| `GetSyncState` | unary | вернуть `last_applied_seq`, `schema_version`, `last_checkpoint_seq`, `action` (PROCEED/NEED_REBASELINE) — вызывать перед сессией, особенно после сбоя |
| `SubmitSchema` | unary | передать структуру всех таблиц; обязателен до первой сессии и при изменении структуры |
| `StreamChanges` | bidi stream | основной поток: `SessionStart → ChangeRecord* → SessionEnd`; сервер шлёт `SessionOpened`, `Ack*`, `SessionCommitted` либо `ServerError` |

### 2.3 Жизненный цикл сессии (одна сессия = один batch)
- `SessionStart{ mode, first_seq, schema_version, client_session_id }`
- `ChangeRecord{ table, op, seq, key, data, source_ts }` — 0..N, `seq` строго возрастает
- `SessionEnd{ last_seq, per_table{inserts,updates,deletes}, content_hash }`
- Сервер: `SessionOpened{ server_session_id, server_last_seq, action, resume_from_seq }`,
  `Ack{ acked_seq }` (прогрессивно, каждые ~100 записей), `SessionCommitted{ committed_seq, segment_s3_key }`.

### 2.4 Правила `seq`
- `seq` — **на сайт** (не на таблицу), монотонный, строго возрастающий, без пропусков.
- `DELTA`: `first_seq` должен быть `server_last_seq + 1`. Разрыв → `ServerError{SEQUENCE_GAP, NEED_REBASELINE}`.
- `FULL_SNAPSHOT`: от правила разрыва освобождён (переустанавливает базовую линию).

### 2.5 Режимы (`SessionMode`)
- `DELTA` — инкрементальные изменения (периодические сессии).
- `FULL_SNAPSHOT` — бутстрап / re-baseline; **все записи = INSERT**.
- `CONTINUOUS` — долгоживущий поток; сервер «запечатывает» сегмент каждые ~100 записей и шлёт
  `SessionCommitted` на каждый сегмент; **`SessionEnd` не отправляется**.

### 2.6 Схема и ключи
- `TableSchema{ columns[], primary_key[], unique_keys[] }`; `Column{ name, type (PG-тип-строкой), nullable }`.
- `primary_key` пустой ⇒ таблица **keyless**: ключ = все колонки.
- **Keyless: `UPDATE` запрещён** — любое изменение = `DELETE` + `INSERT`. Keyed: разрешены I/U/D.

### 2.7 Типизация значений (`Value`, oneof)
- Типы: `is_null` (true ⇒ SQL NULL), `int_value`, `double_value`, `string_value`, `bool_value`,
  `decimal_value` (точное число строкой), `bytes_value`.
- **Различать NULL и «поле отсутствует»**: для частичного `UPDATE` `data` содержит только изменённые
  колонки; явный NULL передаётся как `is_null=true`.
- `INSERT`: полная строка; `UPDATE`: изменённые колонки; `DELETE`: `data` пустой, `key` обязателен.
- Точность: `numeric/decimal`, `date`, `timestamp` передаются **строкой** (ISO/decimal), не как float.

### 2.8 Восстановление и сверка
- `RecoveryAction`: `PROCEED` / `RESUME_FROM` (повтор с `resume_from_seq`) / `NEED_REBASELINE`.
- На `SessionEnd` сервер сверяет per-table счётчики; несовпадение → `ServerError{RECONCILIATION_FAILED}`,
  коммита нет.
- ⚠️ Текущие ограничения сервера (важно для клиента): **staging для RESUME_FROM хранится в памяти**
  (теряется при рестарте сервера или по TTL → клиент должен уметь делать gap-detection / re-baseline).
- ✅ Обновление (ревью r4, 2026-07-08): `content_hash` **сверяется end-to-end** при непустом значении
  (`RECONCILIATION_FAILED` при несовпадении), канонформа length-prefixed, double кодируется битовым
  паттерном IEEE-754 — см. `docs/delta-client-v2-guide.md`. Также теперь валидируется `last_seq`.
  Открытый вопрос по TLS (I1) остаётся: сервер пока plaintext.

## 3. Вопросы клиенту

> Прошу ответить по пунктам — ответы фиксируют контракт и закрывают открытые места.

### A. Источник данных и CDC
- **A1.** Что является источником (DBF-файлы, PostgreSQL, иное)? Несколько источников?
- **A2.** Как детектируются изменения (диф снапшотов/файлов, триггеры, WAL/logical replication, опрос)?
- **A3.** Режим работы: периодические выгрузки (раз в N минут) или непрерывный поток?
  Какой ожидаемый интервал/латентность доставки изменения до сервера?
- **A4.** Объёмы: число таблиц; типичный и пиковый размер пачки изменений (строк и МБ); размер
  строки (есть ли крупные поля/`bytea`)?

### B. Идентификация и `seq`
- **B1.** Можете ли вы генерировать **на сайт** монотонный, строго возрастающий `seq` **без пропусков**,
  переживающий рестарт клиента? Как он персистится?
- **B2.** `seq` общий на сайт по всем таблицам. Подтверждаете, что готовы вести единый счётчик
  (а не per-table)?
- **B3.** Как восстанавливаете `seq` после сбоя — синхронизируете с `GetSyncState.last_applied_seq`?

### C. Ключи и схема
- **C1.** У всех таблиц есть стабильный первичный ключ? Где нет — готовы работать как keyless
  (правило: **никаких `UPDATE`, только `DELETE`+`INSERT`**)?
- **C2.** Меняется ли структура таблиц в проде? Как вы будете детектировать изменение и вызывать
  `SubmitSchema` (и менять `schema_version`)?
- **C3.** Как маппите типы источника → PG-типы для `Column.type` (дайте таблицу соответствий)?

### D. Значения и семантика операций
- **D1.** Для keyed `UPDATE` шлёте **только изменённые колонки** или всю строку?
- **D2.** Как различаете «значение = NULL» и «колонка не менялась/отсутствует»?
- **D3.** Можете отдавать точные `numeric/decimal`, `date`, `timestamp` **строкой** (а не float/локальным форматом)?
- **D4.** Бывают ли в источнике дубликаты строк в keyless-таблицах (одинаковые во всех колонках)?

### E. Сессии и режимы
- **E1.** Какой режим планируете основным: периодический `DELTA` или `CONTINUOUS`?
- **E2.** Как формируете границы сессии/батча (по времени, по числу строк, по транзакции источника)?
- **E3.** Используете ли `client_session_id` для идемпотентности? Как генерируете?
- **E4.** Есть ли в источнике время коммита для `source_ts`? Нужно ли сохранять границы транзакций?

### F. Бутстрап и восстановление
- **F1.** Как делаете первичную загрузку — полный `FULL_SNAPSHOT` (все INSERT)? Объём первой загрузки?
- **F2.** По `NEED_REBASELINE` можете ли по требованию переотдать полный снапшот?
- **F3.** При обрыве посреди сессии: буферизуете ли неподтверждённые (`Ack`) записи и готовы ли
  повторить с `resume_from_seq`? Учитывая, что серверный resume-staging — **в памяти** и теряется при
  рестарте сервера, какой у вас фолбэк (gap-detection → re-baseline)?
- **F4.** Поведение на `ACTIVE_SESSION_EXISTS` (один активный сеанс на сайт): как обрабатываете?

### G. Сверка и целостность
- **G1.** Можете считать per-table счётчики I/U/D для `SessionEnd`?
- **G2.** `content_hash`: предлагаете алгоритм и канонизацию (по каким полям, порядок, кодировка),
  чтобы сервер и клиент считали одинаково? (Сейчас сервер сверяет счётчики; хэш — на согласование.)

### H. Аутентификация
- **H1.** Какой флоу токена используете: Device Flow или deprecated Basic-auth `domain:clientSecret`?
- **H2.** Где и как храните `refresh_token`? Как обновляете access-токен на долгих стримах/reconnect?
- **H3.** Сколько сайтов обслуживает один экземпляр клиента? (токен на сайт — нужно ли вести пул токенов)

### I. Транспорт и эксплуатация
- **I1.** Нужен ли **TLS** на gRPC (сейчас plaintext)? Требования по сертификатам/mTLS?
- **I2.** Сетевая топология (клиент в Parallels-VM/контейнере/отдельный хост), файрвол, доступ к :8080 и :9090.
- **I3.** Ограничение размера gRPC-сообщения (дефолт 4 МБ): ожидаются ли крупные строки/пачки сверх лимита?
- **I4.** Версии: платформа .NET, gRPC-библиотека; кодген из нашего `.proto` или нужен published-пакет?
- **I5.** Поведение на временную недоступность сервера: ретраи, бэкофф, гарантии доставки (at-least-once?).
